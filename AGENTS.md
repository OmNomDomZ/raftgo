# AGENTS.md

Инструкции для агентов в репозитории `raftgo`: собственная реализация Raft и
KV на Go (версия из `go.mod`, сейчас 1.27.1). Рабочий код уже существует.
`CLAUDE.md` отсутствует; источники требований — документы ниже.

## С чего начать

1. [Kanban.md](Kanban.md) — очередь задач с постоянными ID.
2. [docs/stages.md](docs/stages.md) — границы четырёх этапов, API и модель памяти.
3. [docs/tasks.md](docs/tasks.md) — зависимости, объём и критерии каждой задачи.
4. [docs/delivery.md](docs/delivery.md) — ветки, передача работы и проверка сдачи.
5. [README.md](README.md), [docs/onboarding.md](docs/onboarding.md) — разбор
   полного прототипа. Storage уже переведён в память. Приоритет для доработок
   у `docs/stages.md`.

Пользователь может поручить одну карточку фразой «Выполни S2-API».
Прочитай её, зависимости и контракт этапа. Если зависимости не готовы,
сообщи конкретные недостающие ID; не реализуй их молча внутри другой задачи.
Пометь карточку «В работе», после проверок — «Готово». Задача уже разрешена
поручением пользователя: обычные правки и проверки не требуют подтверждения.

## Ветки и объём

- Единственная основная ветка — `main` (не создавать отдельный `master`).
  Здесь живут полный рабочий код, in-memory Storage, UI, инфраструктура,
  `autokanban`, Kanban.md и docs. Все карточки выполняются последовательно
  непосредственно в main, с осмысленными атомарными коммитами.
- Один checkout `/home/bogdan/rafting`. Не создавать task-ветки, worktree,
  клоны или копии папок для карточек. Перед новой карточкой checkout чистый.
  Чужие изменения не коммитить и не удалять: при занятом checkout остановиться
  и назвать препятствие. Сохранять незавершённую работу при ошибке.
- `lab1`, `lab2`, `lab3`, `lab4` — только проверенные снимки для сдачи.
  Они накопительные по возможностям: в labN нет будущего кода, API, UI и тестов.
  Не скрывать будущие функции флагами или выключенными маршрутами.
  Это ограничение относится к labN; полный код main сохранять.
- Снимок готовится только в DEMO в том же checkout на временной ветке
  `snapshot/labN`, от явно записанного SHA main. Отфильтровать будущие функции,
  убрать контроллер/канбан/личные настройки, проверить точный SHA и только
  после успеха создать `labN`. При неудаче оставить временную ветку и вернуться
  в main после сохранения работы. Не выдавать её за принятую labN.
  Подробности — docs/delivery.md. Принятые labN без явной команды не перемещать.
- Не разрабатывать в labN, не мержить снимки обратно в main. Исправления
  делать в main; пересдача снимка — отдельное явное поручение с проверками.
- Старые reference/prepare/stage/task/chore ветки сохраняются как история.
  Они больше не базы разработки или общий журнал. Не переписывать их.
- Поручение карточки разрешает её локальные коммиты в main. Push и force-push
  без явной команды запрещены. `run --max-tasks N` явно разрешает контроллеру
  последовательно выполнить до N доступных карточек; перед DEMO он останавливается.
  При обычном поручении не запускать другие карточки или агентов.

## Архитектура и safety

- Фактическое дерево: `raft/`, `storage/`, `transport/`, `server/`, `kv/`,
  `cmd/raftgo/`, `scenarios/`. UI предстоит добавить в `server/`.
- Цель: только in-memory Storage, без файлов лога/состояния, `data_dir`,
  fsync, каталогов блокировки и data volumes. Конфиги и stdout-логи допустимы.
- Считать память безопасным хранилищем в модели задания. Не терять
  `currentTerm`, `votedFor` и лог при моделируемых отказах. Для демонстраций
  использовать pause/unpause или сетевую изоляцию; не заменять stop/start
  на пустое Storage того же ID. Полный новый запуск — новый пустой кластер,
  а не безопасное восстановление прежнего. Подробнее — `docs/stages.md`.
- `raft/` зависит от интерфейсов Storage, Transport, Clock; не от конкретных
  HTTP, `time.Sleep` и KV. Для core-тестов — fake-транспорт и виртуальное время.
- Каждое изменение `raft/` сопровождается тестами соответствующих свойств:
  Election Safety, Log Matching, Leader Completeness, State Machine Safety
  (только применимых к этапу). Happy path недостаточен.
- Не добавляй сторонние реализации Raft как зависимость.
- Диагностический статус локален; несколько опросов не образуют атомарный
  снимок кластера. Не выдумывай историю голосов из текущего `votes`.
- KV меняется только при apply подтверждённой команды; CAS и lock — одна
  команда каждый. GET KV требует кворумного барьера и ожидания apply.
- `504` означает неизвестный исход, не откат. UI и клиент не повторяют
  изменяющие запросы автоматически. Не ослабляй протокол ради упрощения сдачи;
  при противоречии остановись и явно объясни его.

## Проверки и завершение

```sh
go build ./...
go test ./...
go test -race ./...   # обязательно перед готовностью любой задачи
go vet ./...
gofmt -l .           # вывод должен быть пуст
```

При наличии `.golangci.yml` запускать `golangci-lint run ./...` вместо отдельного
`go vet`. Не меняй версию Go для обхода проблемы окружения. Приложи реальный
вывод/результат проверок; недоступный toolchain или Docker — ограничение,
а не успешный чек. Документационные задачи тоже проходят обязательный race-чек.
Для кода/API/UI дополнительно проверки из карточки; перед приёмкой этапа —
все сценарии, доступные на этом этапе, и ручной прогон UI.

В отчёте: ID, ветка и база, изменённые файлы, поведение, выполненные проверки,
ограничения и следующий доступный ID. Коммиты осмысленные и атомарные.
