# CLAUDE.md

Этот файл — инструкция для Claude Code при работе в этом репозитории.

## О проекте

Учебный проект (вуз): реализация консенсус-протокола **Raft "с нуля"** (без готовых
библиотек типа hashicorp/raft) и **KV-хранилища поверх него** на Go.

Команда — 2 человека. Рабочий процесс: задача декомпозируется на подзадачи, каждая
подзадача берётся в отдельную ветку, реализуется (в том числе с помощью Claude Code),
покрывается тестами, проходит ревью и мержится в `main` через PR.

Смежный файл [AGENTS.md](./AGENTS.md) содержит инструкции для агентов в целом
(build/test/lint команды, структура репо) — читай его тоже, он не дублирует, а
дополняет этот файл.

## Архитектура (целевая)

- `raft/` — реализация протокола Raft: leader election, log replication,
  safety-инварианты, персистентность состояния (currentTerm, votedFor, log),
  таймауты и random election timeout. Опционально по мере необходимости:
  log compaction / snapshotting, membership changes.
- `kv/` — KV-хранилище (state machine), применяющее закоммиченные записи из Raft-лога.
  Простой интерфейс `Apply(command) -> result`, снапшоты состояния для восстановления.
- `transport/` — сетевой слой между узлами Raft (RPC: RequestVote, AppendEntries,
  InstallSnapshot). Должен быть заменяем: в тестах — in-memory/fake транспорт с
  возможностью симулировать задержки, потери пакетов и партиции сети.
- `storage/` — персистентное хранилище лога и метаданных узла (например, на базе
  файлов или BoltDB/Pebble — конкретный выбор фиксируется в момент реализации,
  не меняй его без согласования, если он уже выбран).
- `server/` или `cmd/` — процесс узла, который поднимает Raft + KV + сетевой сервер
  и отдаёт клиентский API (например gRPC или простой TCP/HTTP протокол).
- `client/` — клиентская библиотека/CLI для похода в кластер (нужно уметь находить
  лидера, ретраить на смену лидера).

Если структура в репозитории на момент работы отличается от описанной — доверяй
фактическому состоянию кода (`ls`, `go list ./...`), а не этому файлу, и предложи
обновить этот раздел.

## Рабочий процесс (важно соблюдать буквально)

1. **Никогда не пушь и не мержь в `main` напрямую.** Вся работа — в feature-ветках.
   Формат имени ветки: `<автор>/<номер-или-имя-задачи>-<короткое-описание>`,
   например `bogdan/3-leader-election`.
2. Каждая ветка = одна декомпозированная подзадача (не "весь Raft", а, например,
   "RequestVote RPC и голосование", "AppendEntries + repair лога",
   "election timeout и восстановление после сплита сети", "KV Apply + снапшот").
3. Перед тем как писать код — убедись, что понимаешь, к какому куску архитектуры
   относится задача, и не выходи за её границы (не тащи заодно рефактор соседних
   модулей, если не попросили).
4. Обязательные тесты для Raft-логики:
   - unit-тесты на отдельные переходы состояний (Follower/Candidate/Leader);
   - детерминированные тесты с fake-транспортом, проверяющие safety-свойства
     (Election Safety, Leader Append-Only, Log Matching, Leader Completeness,
     State Machine Safety — из оригинальной статьи Raft);
   - тесты на партиции сети / потерю сообщений / рестарт узла с восстановлением
     состояния из storage.
   - `go test -race ./...` должен быть чистым — конкурентность в Raft легко ловит
     гонки, это не опционально.
5. Коммиты — осмысленные, на английском или русском (следуй тому, что уже
   используется в истории репозитория), в императиве ("add", "fix", а не "added").
   Не смешивай несвязанные изменения в одном коммите.
6. PR перед мержем в `main` должен содержать: что сделано, как протестировано,
   какие safety-свойства затронуты/проверены. Ревью — вторым участником команды
   обязательно, даже если код написан агентом.
7. Не считай задачу выполненной, пока не прогнаны тесты (`go test ./...` и
   `go test -race ./...`) и не пройден `go vet`/линтер, если он настроен.

## Чего агенту делать не следует

- Не подменяй консенсус-алгоритм готовыми библиотеками (`hashicorp/raft`, etcd raft
  и т.п.) — цель проекта — самостоятельная реализация. Разрешено смотреть на их
  публичный API/тесты как референс для идей, но не копировать реализацию.
- Не ослабляй safety-инварианты Raft "для простоты" (например, коммит записи без
  проверки кворума, применение незакоммиченных записей в state machine) — если
  кажется, что тест мешает и его легче упростить, чем починить логику, — это красный
  флаг, нужно остановиться и явно сказать об этом, а не тихо обойти.
- Не переписывай уже смерженный в `main` код другого участника без явного запроса —
  предложи изменения, но не делай их в одностороннем порядке в чужой ветке.
- Не добавляй тяжёлые внешние зависимости (сервисные шины, оркестраторы) без
  необходимости — это учебная реализация, минимализм — часть ценности работы.
- Не коммить и не пушить автоматически без запроса — коммит делается по явной
  просьбе, ветку/PR открывает пользователь (или по явной просьбе агент).

## Стиль кода

- `gofmt`/`goimports` перед коммитом.
- Явная обработка ошибок, без `panic` во время нормальной работы узла (кроме явно
  невосстановимых invariant-нарушений, и то — с пояснением в комментарии почему).
- Логика Raft-протокола (переходы состояний, таймеры, RPC-обработчики) должна быть
  тестируема без реальной сети и реального времени — используй интерфейсы для
  транспорта и источника времени/таймеров, а не `time.Sleep`/`net` напрямую внутри
  core-логики.
- Комментарии — только там, где не очевидно "почему" (например, ссылка на конкретный
  пункт статьи Raft, который реализует кусок кода), не пересказывай "что" делает код.
