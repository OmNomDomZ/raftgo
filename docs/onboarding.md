# Онбординг: от первого запуска до защиты

> **Статус:** полный прототип переведён на безопасную память (B1–B2).
> Выделение четырёх этапов ещё впереди; см. [контракт](stages.md),
> [карточки](tasks.md) и [порядок сдачи](delivery.md). Экран выборов доступен на `GET /` каждого узла.

Проект реализует реплицированный словарь `string → string`. Каждый процесс
содержит собственный Raft, собственный лог в Memory и собственный KV в памяти.
Клиент обращается к HTTP API; лидер упорядочивает изменения через Raft, а все
реплики выполняют подтверждённые команды в одинаковом порядке.

## Маршрут знакомства

1. Выполни [быстрый запуск](../README.md#запуск-пяти-нод-и-rest-api) и практикум ниже.
   Найди лидера, запиши значение и сравни локальные логи двух узлов.
2. Прочитай в README разделы от [терминов](../README.md#зачем-нужен-raft)
   до [безопасных чтений](../README.md#как-безопасно-читать).
   Объясни разницу между term, index, commit и apply.
3. Пройди путь записи и чтения ниже с открытым кодом. Затем разбери CAS,
   блокировки и восстановление.
4. Запусти тесты и [четыре сценария сдачи](../scenarios/README.md).
   Свяжи каждый наблюдаемый результат с конкретным правилом протокола.
5. Ответь на вопросы в конце без подсказок. Для защиты недостаточно показать
   `PASS`: нужно объяснить, почему меньшинство не подтверждает операции.

Ядро `raft` зависит от интерфейсов `Storage`, `Transport`, `Clock`, а не от
HTTP или KV. `kv` ничего не знает о сети и выборах. `server` связывает их:
это место, где «команда закоммичена» превращается в результат клиентской операции.
Сторонней реализации Raft в зависимостях нет.

```text
клиент → server.Handler → kvRequest → Raft.Start
                                       ↓
                         Storage + Transport → RPCHandler других узлов
                                       ↓ большинство, commit
                             ApplyCh на каждой реплике
                                       ↓
                          API.Consume → Store.Apply
                                       ↓
                       результат ожидающему HTTP-запросу
```

## Одна запись от HTTP до ответа

Рассмотрим `PUT /kv/message` с `{"value":"hello"}`.

1. `kvRequest` проверяет ключ и JSON. Ключ — 1–1024 байта, итоговая внутренняя
   команда вместе с префиксом — не больше 65536 байт. Неизвестные поля JSON
   отклоняются. Значение обязательно должно быть строкой, в том числе пустой.
2. Создаётся `kv.Command{Op:"put", Key:"message", Value:"hello"}`.
   В Raft отправляются байты `raftgo:kv:v1:` + JSON. Сам Raft их не разбирает.
3. `Raft.Start` принимает запись только на лидере, сохраняет её локально,
   будит репликаторы и возвращает `(index, term)`. Это ещё не успех для клиента.
   Follower отвечает через `failure`: 307 на известного лидера или 503.
4. Репликаторы отправляют `AppendEntries`. Получатель проверяет опору
   `PrevLogIndex/PrevLogTerm`, сохраняет изменения и только потом подтверждает.
   Лидер обновляет `matchIndex`; большинство для записи своего term позволяет
   продвинуть `commitIndex`. Для пяти узлов нужны три, включая лидера.
5. `raft.apply` доставляет подтверждённые записи в `ApplyCh` по порядку.
   Лидер не ждёт применения на всех follower перед ответом клиенту.
6. `API.Consume` распознаёт префикс, декодирует команду и вызывает `Store.Apply`
   под `API.mu`. Результат сохраняется в `results[index]` вместе с term.
   Затем обновляется `API.applied` и закрывается `changed`, пробуждая ожидающих.
7. `waitApplied` дожидается нужного индекса. Обработчик проверяет term результата:
   после смены лидера неподтверждённую запись на той же позиции могли заменить.
   Успешный PUT возвращает 200, например `{"value":"hello","index":2}`.
   Индекс здесь условный: no-op и другие операции тоже занимают позиции.

Проверка состояния и подписка на `changed` происходят под одним mutex.
Поэтому даже если применение завершилось раньше ожидания, уведомление не теряется:
обработчик увидит уже увеличенный `applied`. `Store` собственного mutex не имеет;
его вызовы сериализует `API`.

`/entries` идёт похожим путём, но не выполняет строку как команду KV.
`POST /entries {"command":"SET message hello"}` добавит только диагностическую
запись. Зарезервированный KV-префикс через этот маршрут отправлять нельзя.

## Как проходит GET

`GET /kv/message` вызывает `ReadIndex`, затем `waitApplied`, затем `Store.Get`
под mutex. GET не добавляет запись в Raft-лог.

ReadIndex требует коммита записи текущего term и свежего подтверждения
большинства после начала раунда чтения. После этого приложение ждёт применения
до возвращённого индекса. Просто проверить `role == Leader` недостаточно:
изолированный старый лидер некоторое время ещё считает себя лидером.
CheckQuorum заставляет его отступить при потере большинства, но не заменяет
барьер конкретного чтения.

`/status`, `/election`, `/log` — локальная диагностика без такого барьера.
Их можно читать у follower, чтобы увидеть отставание. Поле `running` означает
работающий цикл Raft, а не готовность обслуживать линейризуемые запросы.

## CAS и блокировки

CAS — одна команда `cas` в логе: сравнение `expected` и изменение `value`
выполняются вместе внутри `Store.Apply`. Если два клиента меняют `a` на разные
значения, один первым увидит `a` и получит 200; следующий увидит изменённое
значение и получит 409. Последовательность GET → PUT такой гарантии не даёт.
Если успешный CAS оставляет значение равным `a`, следующий CAS с `expected=a`
тоже может быть успешным. Сравнивается значение, а не версия: случай `a → b → a`
не обнаруживается (ABA).

Неуспешный CAS тоже занимает запись в логе: все реплики вычисляют один результат
на одном состоянии. То же относится к отказам CRUD/lock после принятия команды.
Ошибки проверки HTTP-тела отсекаются до Raft.

Блокировки хранятся в отдельной карте `locks`, поэтому можно заблокировать
несуществующий ключ; удаление значения не снимает lock. Захват — команда `lock`,
токен — десятичная строка индекса этой записи. Он одинаков на всех репликах,
а следующий успешный захват имеет больший индекс. Нет генерации токена по
локальному времени или случайному числу при применении. Индексы сравниваются
как числа, а не как строки; между успешными захватами возможны пропуски.
Владелец сохраняет токен до unlock: удаление и пересоздание значения, смена
лидера и replay подтверждённого префикса его не меняют. После unlock токен
недействителен; у следующего владельца будет другой, больший токен.
Replay означает применение лога к новой Store с исходными индексами, а не
повторную отправку запросов: дедупликации клиентских команд нет.

`access` проверяет токен перед CRUD, CAS и GET:

| Состояние | Запрос | Результат проверки доступа |
| --- | --- | --- |
| Ключ занят | Без токена или чужой токен | 423 |
| Ключ занят | Текущий токен | Доступ разрешён |
| Ключ свободен | Без токена | Доступ разрешён |
| Ключ свободен | Старый токен | 409 |

Повторный захват занятой блокировки даёт 423 даже владельцу: lock не реентерабельный.
Unlock требует токен; без токена на свободном ключе будет 409.
Блокировки без TTL и автоматического снятия при падении клиента. Токен нужно
сохранить до освобождения. Это координация доверенных клиентов, не аутентификация.
Внешняя система сама должна проверять fencing-токены, если защищает ими ресурс.

## Безопасная память и возврат узла

`storage.Memory` хранит term, голос и лог в RAM. Диск не используется.
Отказ на стенде — `docker compose pause`, возврат — `unpause`: вся память
процесса, включая KV, locks и результаты запросов, остаётся на месте.
HTTP и RPC паузной ноды недоступны; runner использует короткие таймауты.

Нельзя делать stop/start отдельной ноды и возвращать пустую Memory с прежним
ID в продолжающийся кластер: забытый голос допускает второй голос в term.
Полное удаление всех процессов и новый запуск означает новый пустой кластер.
Не используйте в нём прежние lock-токены; fencing монотонен только внутри
одной жизни кластера.

В unit-тестах можно пересоздать Raft с тем же объектом Memory. Для новой
машины состояний проигрывается только подтверждённый префикс; commit index
узел узнаёт от лидера или после коммита записи своего term. `Consume`
продвигает applied index также на no-op и произвольных `/entries`.

## Практикум на основном Docker-стенде

После `docker compose up --build -d` подожди выборов. Команды ниже используют
новый ключ при каждом запуске; нужны bash, curl и Python 3 для извлечения токена.

```sh
base=http://localhost:8001
key="onboarding-$(date +%s)-$$"
curl -sS "$base/status" | python3 -m json.tool
curl -sS -i -L --max-redirs 5 -X PUT "$base/kv/$key" \
  -H 'Content-Type: application/json' --data '{"value":"hello"}'
# 200, value=hello
curl -sS -i -L --max-redirs 5 "$base/kv/$key"
curl -sS -i -L --max-redirs 5 -X POST "$base/kv/$key/cas" \
  -H 'Content-Type: application/json' --data '{"expected":"hello","value":"world"}'
# 200; повтор этой CAS даст 409 и value=world
lock_reply=$(curl -fsS -L --max-redirs 5 -X POST "$base/kv/$key/lock")
printf '%s\n' "$lock_reply"
token=$(printf '%s' "$lock_reply" | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')
curl -sS -i -L --max-redirs 5 "$base/kv/$key"
# 423
curl -sS -i -L --max-redirs 5 "$base/kv/$key" -H "X-Lock-Token: $token"
# 200, value=world
curl -sS -i -L --max-redirs 5 -X DELETE "$base/kv/$key/lock" -H "X-Lock-Token: $token"
# 200
curl -sS http://localhost:8001/log | python3 -m json.tool
curl -sS http://localhost:8002/log | python3 -m json.tool
```

Убедись, что захват вернул 201 и токен извлечён, прежде чем продолжать.
Сравни подтверждённые префиксы логов после догоняющей репликации. KV-команды
видны с префиксом и JSON, а после выборов присутствует `noop`.

Для демонстрации отказов удобнее отдельный [стенд сценариев](../scenarios/README.md):
он использует порты 18001–18005 и отдельные процессы. Запусти `python3 scenarios/run.py all`
после сборки этого стенда. Runner сам определит лидера, поставит нужные ноды на паузу,
проверит результаты и снимет все паузы даже после ошибки.

Для разработки без Docker нужен Go не ниже версии из `go.mod` (1.27.1).
Минимальный однопроцессный запуск из корня:

```sh
cat > /tmp/raftgo-local.json <<'JSON'
{
  "listen": "127.0.0.1:8001",
  "rpc_listen": "127.0.0.1:9001",
  "members": [
    {"id":"node1","rpc_url":"http://127.0.0.1:9001","api_url":"http://127.0.0.1:8001"}
  ]
}
JSON
go run ./cmd/raftgo -config /tmp/raftgo-local.json -id node1 -log-level debug
```

Порт 8001 должен быть свободен. Одного узла достаточно для чтения кода и API,
но он не демонстрирует отказоустойчивость. Для нескольких процессов нужны
отдельные конфиги с разными `listen`/`rpc_listen` и одинаковым полным `members`.
Каждый запуск создаёт пустую Memory; состав работающего кластера фиксирован.

Из корня: `go build ./...`, `go test -race ./...`, `go vet ./...`, `gofmt -l .`.
Для принудительного повторного запуска тестов добавь `-count=1`.

| Что объяснить или проверить | Где находится проверка |
| --- | --- |
| Нельзя голосовать дважды в term, в том числе после рестарта | [raft/handlers_test.go](../raft/handlers_test.go) |
| Коммит только с большинством; замена неподтверждённого хвоста | [raft/replication_cluster_test.go](../raft/replication_cluster_test.go) |
| Старый лидер не обслуживает безопасные чтения | [raft/read_test.go](../raft/read_test.go) |
| Сбой сохранения term не разрешает продолжать лидерство | [raft/stepdown_test.go](../raft/stepdown_test.go) |
| Детерминированность KV, токены, доступ под блокировкой, ABA | [kv/store_test.go](../kv/store_test.go), [kv/atomic_test.go](../kv/atomic_test.go) |
| Гонки CAS/lock, failover, fencing и replay с тем же Memory | [server/kv_atomic_test.go](../server/kv_atomic_test.go) |
| Replay, барьеры no-op и обычных записей | [server/replay_test.go](../server/replay_test.go) |
| Реальные HTTP-редиректы, коммит и смена лидера | [server/http_test.go](../server/http_test.go) |
| Memory: копирование, атомарность, конкурентный доступ и пересоздание Raft | [storage/memory_test.go](../storage/memory_test.go) |

В Raft-тестах время и транспорт подменяются; интеграционные HTTP-тесты и Docker
работают с реальными таймингами. Тест consumer replay подаёт `ApplyMsg` напрямую;
pause/unpause всех процессов с сохранением RAM проверяют сценарии 3 и 4.

| Симптом | Что проверить |
| --- | --- |
| 307 | Нормальный ответ follower; используй `curl -L`, проверь доступность `api_url` |
| 503 сразу после старта | Дождись выборов; проверь большинство, RPC-адреса и логи |
| 503/504 без большинства | Ожидаемый отказ от успешной операции; восстанови связь/ноды |
| 504 при записи | Исход неизвестен: запись могла остаться в логе и позже примениться; это не откат |
| 409 | Читай `error`: CAS не совпал, ключ уже существует, токен устарел или запись заменена |
| 423 | Ключ заблокирован; нужен токен текущего захвата |
| После unpause KV ещё не читается | Дождись выборов, кворумного барьера и догоняющей репликации |
| Docker-имя `node1` не разрешается на хосте | Для запуска без Docker нужны локальные RPC URL |

В debug-логах связывай `kv proposed`, `entry applied`, `kv applied` по index/term
и ID ноды. Request ID локален процессу и не является ID команды для дедупликации.
Таймаут HTTP-обработчика KV — 5 секунд; ошибка на этапе ReadIndex проходит через
`failure` как 503, ожидание применения может дать 504. Значения и токены не
добавляются в debug-сообщения, но доступны через диагностический `/log`.

## Вопросы для защиты

| Вопрос | Что должно быть в ответе |
| --- | --- |
| Почему из пяти узлов нужны три? | Большинство `N/2+1`, пересечение кворумов; при потере двух работа продолжается |
| Могут ли два узла считать себя лидером? | Да, в разных term при разделении; избранных лидеров одного term не больше одного |
| Почему длинный лог не обязательно актуальнее? | При голосовании сначала сравниваются последние term, затем индексы |
| Почему недостаточно сохранить запись на лидере? | Неподтверждённый хвост может быть заменён; нужен коммит и применение своей записи |
| Зачем no-op после выборов? | Коммит записи своего term подтверждает предыдущий префикс и открывает барьер чтений |
| Почему нельзя напрямую коммитить запись старого term по числу копий? | Правило Raft требует запись текущего term; предыдущие коммитятся вместе с её префиксом |
| Зачем проверять term результата, если есть index? | Незакоммиченную позицию мог занять другой лидер другой командой |
| Почему GET требует сети? | Нужно подтвердить лидерство большинством после начала чтения и дождаться apply |
| Почему CAS атомарен? | Проверка и замена выполняются одной командой в общем порядке |
| Чем lock отличается от локального mutex? | Состояние lock реплицируется через Raft; локальный mutex лишь сериализует доступ внутри процесса |
| Почему блокировка переживает смену лидера? | Она записана в подтверждённом логе; token воспроизводится из индекса |
| Можно ли безопасно повторить запрос после 504? | Нет гарантии exactly-once: дедупликации нет, первый запрос мог выполниться |
| Что сохраняется при pause? | Вся RAM: term, голос, лог, KV и locks; завершение процесса всё теряет |

Границы проекта: фиксированный состав, нет snapshots/компакции, PreVote,
дедупликации, транзакций над несколькими ключами и TTL блокировок. Лог и таблица
результатов растут в памяти. API без TLS и аутентификации
рассчитан на доверенный локальный стенд. Safety проверяется тестами конкретных
сценариев; формального доказательства и тестов всех возможных сбоев здесь нет.
