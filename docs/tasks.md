# Карточки для агентов

Очередь и статусы — [Kanban.md](../Kanban.md). Контракт сдаваемых снимков —
[stages.md](stages.md), процесс — [delivery.md](delivery.md).
Все новые карточки выполняются прямо в чистом `main`, в одном checkout.
B0–B2 и S1-CORE уже выполнены; их результаты и SHA сохранены в delivery.

`main` содержит полную реализацию. Требования отсутствия будущих возможностей
относятся к `labN`, который выделяется и проверяется только в DEMO.
Не удалять из main работающие log/KV/CAS/lock ради ранней лабораторной.
Проверки карточек в main должны сохранять тесты полной реализации; проверки
отсутствия будущих API/полей/кода выполняются на кандидате labN в DEMO.
Наличие прототипа не заменяет проверку контракта и не делает карточку готовой.

Для каждой карточки обязательны build, test, race, vet/lint, gofmt из AGENTS.
Ниже дополнительные критерии. При нехватке зависимости назвать ID.
Сдаваемые labN создаются только после всех проверок DEMO; никаких worktree.

## R1 — Общее ожидание apply для строк и KV

- **База/цель:** `main`. **После:** S4-DEMO.
- **Статус:** выполнено. Приоритет высокий, риск средний.
- **Применимость:** lab2–lab4; устранение дублирования проявляется в lab3–lab4.
- **Основание:** `server/http.go:appendEntry` содержит собственный цикл ожидания
  `applied/changed`, повторяющий `server/kv.go:waitApplied`. На lab2 цикл уже
  существует, но KV ещё нет. Точные исследованные SHA — [refactoring.md](refactoring.md).
- **Рефакторинг:** перенести существующий `waitApplied` в отдельный
  `server/apply_wait.go`, не зависящий от `kv`; использовать его в appendEntry
  и kvRequest. В appendEntry оставить после ожидания проверку исходной пары
  index/term через лог; в KV оставить проверку term в results. Не объединять
  эти разные способы получения результата в универсальный callback/framework.
- **Сохранить:** атомарное чтение applied и changed под одним mutex, отсутствие
  потерянного уведомления, поведение при уже применённом индексе и отмене,
  существующие границы HTTP-дедлайнов; ответы 201/409/504 и index/term.
  ReadIndex перед ожиданием GET обязателен. 504 не означает откат.
- **Не входит:** изменение Consume, retention results, оптимизация InspectLog,
  новый API ядра, изменение протокола Raft или пересдача снимков.
- **Проверки:** обязательный Go-набор; существующие string_apply, http_entries,
  http_kv, kv_safety, http_atomic тесты. Убедиться в покрытии apply до подписки,
  задержанного consumer, замены записи тем же index с другим term, отмены,
  потери кворума и позднего commit после 504; недостающее покрытие дополнить.
- **Готовность:** единственный цикл ожидания в server, строковый путь не зависит
  от KV, все прежние ответы и safety-тесты сохранены. В будущем снимке lab2
  helper включается без KV/ReadIndex; в lab1 не включается.

- **Рефакторинг:** выделить приватный механизм в `server/ui_forward.go`:
  отправка одного запроса и переход только по разрешённому 307, закрытие Body,

  Сохранить метод/тело/явный токен на каждом разрешённом переходе; Unicode,

  объединение JSON-декодеров, изменение правил CAS/lock или кодировки ключа.
  Небольшая независимая проверка в client остаётся в своём слое.
- **Проверки:** обязательный Go-набор; http_atomic/ui_kv/http_kv тесты.
  Через оба HTTP-входа проверить границы 1024/1025 байт, многобайтный ключ,
  пустой ключ, несколько заголовков, запятую и допустимый пустой токен.
  Для случаев, которые HTTP-транспорт не пропускает (например CR/LF),
  использовать httptest Request/Recorder. Сохранить сценарии владельца,
  чужого и старого токена. Невалидный запрос не добавляет команду в лог.
- **Готовность:** одна реализация каждой серверной проверки, неизменные
  HTTP-ответы. В будущем lab3 отсутствуют helper токена и его тесты.
