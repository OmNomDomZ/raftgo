# Карточки для агентов

Каждый заголовок — одна задача и ссылка с Kanban. Общие требования и API:
[stages.md](stages.md). Работа с ветками и отчётом: [delivery.md](delivery.md).
Статусы карточек и результаты проверок записаны в Kanban и delivery.
Прочитанный код не означает пройденную приёмку.

Для каждой задачи обязательны build, test, race, vet/lint, gofmt из AGENTS.md.
Ниже перечислены дополнительные проверки. Документацию своего этапа обновлять
вместе с изменением. Не брать следующую карточку без поручения.

## B1 — Реализовать Memory Storage

- **База/цель:** `prepare/in-memory`. **После:** B0.
- **Файлы:** новый `storage/memory.go`, тесты, комментарии `raft/storage.go`.
- **Работа:** реализовать существующий Storage в RAM: term/голос, последовательный
  лог, атомарная замена суффикса, mutex, глубокие копии входа/выхода. Сохранить
  абстракцию Storage и семантику ошибок; убрать устаревший дисковый TODO из
  контракта, описать безопасную память. Пока не менять wiring приложения.
- **Готово:** Memory удовлетворяет Storage; данные не меняются через переданные
  срезы/Command bytes; некорректный from не портит хранилище. Новый Raft с тем же
  объектом восстанавливает term/голос/лог и не голосует второй раз в term.
- **Проверки:** concurrent load/save, отсутствие aliasing, truncation,
  границы индекса, restart с тем же Storage, Election Safety и Log Matching.

## S4-CORE — CAS и распределённые блокировки

- **База:** принятая `stage/3-kv`. **Цель:** `stage/4-cas-lock`.
- **После:** S3-DEMO.
- **Файлы:** `kv/store*`, consumer и тесты.
- **Работа:** вернуть CAS/lock/unlock как одиночные реплицируемые команды,
  fencing token из индекса, доступ с токеном; сохранить блокировку независимо

- **Готово:** одинаковые исходы на репликах, смена лидера сохраняет lock;

- **Проверки:** два CAS на одно expected с разными новыми значениями — один
  победитель; два lock — один победитель; чужой/старый/пустой токен, удаление
  и пересоздание значения под lock, replay и монотонность токена в одной жизни.
