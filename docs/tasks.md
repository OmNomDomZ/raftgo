# Карточки для агентов

Очередь и статусы — [Kanban.md](../Kanban.md). Контракт сдаваемых снимков —
[stages.md](stages.md), процесс — [delivery.md](delivery.md).
Все новые карточки выполняются прямо в чистом `main`, в одном checkout.
B0–B2 и S1-CORE уже выполнены; их результаты и SHA сохранены в delivery.

`main` содержит полную реализацию. Требования отсутствия будущих возможностей
относятся к `labN`, который выделяется и проверяется только в DEMO.
Не удалять из main работающие log/KV/CAS/lock ради ранней лабораторной.
Проверки карточек в main должны сохранять тесты полной реализации; проверки
отсутствия будущих API/полей/кода выполняются на кандидате labN в DEMO.
Наличие прототипа не заменяет проверку контракта и не делает карточку готовой.

Для каждой карточки обязательны build, test, race, vet/lint, gofmt из AGENTS.
Ниже дополнительные критерии. При нехватке зависимости назвать ID.
Сдаваемые labN создаются только после всех проверок DEMO; никаких worktree.

- **Зависимости:** нет.

  план и исходные проверки. Теперь план и журнал находятся в main.

## B1 — Реализовать Memory Storage

- **База/цель:** `main`. **После:** B0.
- **Статус:** выполнено, код перенесён в main.
- `storage.Memory`: mutex, атомарность term/голоса и замены суффикса,
  глубокие копии, границы индексов и ошибки без изменения состояния.
- Сохранять тесты concurrent load/save, aliasing, truncation, restart Raft
  с тем же Storage, Election Safety и Log Matching.

## B2 — Перевести приложение и стенды на память

- **База/цель:** `main`. **После:** B1.
- **Статус:** выполнено, код перенесён в main.
- Memory подключён в приложении, файловый backend/data_dir/volumes удалены.
  HTTP/replay-тесты используют Memory; failure-injection ядра сохранён.
- Сценарии используют pause/unpause и finally cleanup. Новый полный запуск
  кластера пустой. Проверены task1–4, cleanup после ошибки и полный сброс.

## S1-CORE — Выделить только выборы

- **База/цель разработки:** `main`. **После:** B2.
- **Статус:** выполнено исторически в `stage/1-election`; SHA в delivery.
- Выделенное ядро выборов и heartbeat — источник для кандидата lab1 в S1-DEMO.
  Повторно удалять log/KV/CAS/lock из main нельзя.
- В lab1 хранить только term/голос, выборы/heartbeat/check quorum и интерфейсы
  Storage/Transport/Clock. Стандартные нулевые логовые поля RPC допустимы.
- Сохранить проверки split vote, повторов/задержек RPC, старших term,
  изоляции меньшинства, restart с тем же Memory и Election Safety.

## S1-API — Состояние выборов без будущих полей

- **База/цель:** `main`. **После:** S1-CORE.
- **Файлы:** `raft/inspect*`, `server/http*`, документация API.
- Реализовать/проверить диагностику выборов: node/members, term/role/leader,
  voted_for и votes без выдуманной истории. Документировать локальность.
  Сохранить полный API main; подготовить выделение статуса выборов в lab1.
- HTTP-тесты: кандидат/follower/лидер, повторный голос, неизвестные маршруты,
  методы и точная семантика полей. В S1-DEMO проверить, что lab1 не содержит
  логовых полей и не обслуживает /entries, /log, CRUD/CAS/lock.

## S1-UI — Экран выборов пяти узлов

- **База/цель:** `main`. **После:** S1-API.
- **Файлы:** встроенные ресурсы `server/`, routing/тесты.
- `GET /`: пять узлов, роли/term/лидер/голоса, автообновление, доступность,
  устаревание. Same-origin `GET /cluster/status` только фиксированных участников,
  короткие таймауты, частичный результат и явная неатомарность.
- Подготовить перенос UI выборов в lab1; main может содержать будущие панели.
  В lab1 при выделении оставить только экран первого этапа.
- Проверить HTML как текст, недоступный узел, pause лидера, отсутствие кворума,
  отсутствие CORS-зависимости. Ручной браузер обязателен.

## S2-CORE — Вернуть строковый Raft-лог

- **База/цель:** `main`. **После:** S1-DEMO.
- **Файлы:** `raft/`, Storage, apply consumer, core-тесты.
- Проверить/доработать существующую репликацию строк: no-op, commit/apply,
  конфликты суффикса, ожидание результата своей пары index/term.
  Не переписывать работающую реализацию и не удалять KV main.
- Для lab2 в DEMO выделить только строковый лог, без KV-кодирования и ReadIndex.
- Проверки: Log Matching, Leader Completeness, Election Safety, State Machine

  переупорядочивание, новый лидер удаляет неподтверждённый хвост.

## S2-API — Add и лог на эндпоинте состояния

- **База/цель:** `main`. **После:** S2-CORE.
- `GET /status` и /election: node и entries из одного InspectLog,
  consistency=local; /log сохранить. POST /entries принимает UTF-8 строку
  до 64 КиБ, отвечает 201 только после apply своей пары index/term.
- Сохранить защиту внутреннего KV-префикса в main; в lab2 нет KV-декодера.
- Проверить пустые/Unicode/повторяющиеся строки, границы размера, неверный JSON,
  307/503/504/409, хвост и no-op, отсутствие автоматического retry записи.

## S2-UI — Добавление строки и наблюдение реплик

  результат показывает index/term и неизвестный исход 504.

- Проверить повторяющиеся/пустые/HTML строки, follower, pause лидера,
  отсутствие большинства, 504 без автоповтора. Ручной браузер.

## S3-API — HTTP CRUD строк

- **База/цель:** `main`. **После:** S3-CORE.
- Четыре метода /kv/{key}, строгий JSON/ключи/размеры; POST 201/409,
  PUT 200, GET/DELETE отсутствующего 404. Успех после apply;
  GET только после кворумного барьера. Редиректы и неизвестный исход.
- Проверить пустые строки/Unicode/JSON-подобные значения, URL-экранирование,
  follower GET/PUT, stale leader GET, reserved /entries, 504 без retry.
  CAS/lock сохраняются в main, удаляются из кандидата lab3.

## S4-CORE — CAS и распределённые блокировки

- **База/цель:** `main`. **После:** S3-DEMO.
- Проверить/доработать CAS/lock/unlock как одиночные реплицируемые команды,
  fencing token из индекса, доступ с токеном, lock независимо от наличия ключа.
  Без TTL/времени/рандома в apply. ABA и время жизни токена документированы.
- Два CAS одного expected с разными новыми значениями — один победитель;
  два lock — один победитель. Чужой/старый/пустой токен, удаление/пересоздание
  ключа под lock, replay, смена лидера и монотонность в одной жизни кластера.

## S4-API — HTTP CAS, lock и unlock

- **База/цель:** `main`. **После:** S4-CORE.
- CAS/lock маршруты, X-Lock-Token для CRUD/GET/CAS/unlock, строгая валидация,
  409/423, redirect с токеном. CAS не реализовывать раздельными GET и PUT.
- HTTP-гонки CAS/lock, все операции под lock, failover/no-quorum,
  неверные тела/методы, потеря ответа без повтора. Успех по index/term после apply.

## S4-CLIENT — Клиентский Go API

- **База/цель:** `main`. **После:** S4-API.
- Новый `client/`: Create/Get/Put/Delete/CAS/Lock/Unlock с context,
  настраиваемым http.Client, ограниченными 307, методом/телом/токеном,
  типизированными 404/409/423/503 и неизвестным исходом 504/сетевой ошибки записи.
- Без скрытых повторов изменяющих запросов; пример двух клиентов,
  ограничения exactly-once, только HTTP API, без CLI/внешних зависимостей.
- httptest: redirect/цикл/отмена/timeout/токен, CAS/lock двумя клиентами,
  разрыв после отправки без повтора команды.

## S4-UI — CAS и владение lock

- **База/цель:** `main`. **После:** S4-API.
- expected/new CAS, захват/освобождение, токен во вкладке владельца,
  явная передача операциям. Чужая вкладка автоматически токен не получает.
- Две вкладки: конфликт CAS, lock отсутствующего ключа, чужой токен,
  отказ после unlock со старым токеном, failover/504 без повтора/auto-unlock.
  Честно показывать потерю токена и отсутствие TTL.
