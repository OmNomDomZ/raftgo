# Контракт четырёх этапов

Это контракт сдаваемых лабораторных, а не заявление об их приёмке.
План составлен по полному прототипу `70782f23fe695d184981dff932c47181f9eadd21`.
После B2 `cmd/raftgo/main.go` использует `storage.Memory`, все API полного
прототипа пока включены сразу. Встроенный экран выборов доступен на `GET /`; внешний
dashboard есть в scenarios/. Runner использует pause/unpause,
включая паузу всех процессов; data volumes и файлового backend больше нет.

Контракт ниже применяется к сдаваемым снимкам `lab1`–`lab4`.
В `main` остаётся полный код всех возможностей, инфраструктура и канбан.
Разработка и проверки карточек идут в main; выделение и приёмка снимка — в DEMO.
Отсутствие будущих функций проверяется в снимке, не удалением работающего кода main.

## Разделение функциональности

Этапы **накопительные**: этап 3 содержит выборы и строковый лог, но ещё не CAS
и lock. На ранней ветке будущего кода нет даже при выключенных маршрутах.
Служебные RPC/типы, необходимые протоколу текущего этапа, допустимы.
Документы плана могут описывать будущие этапы, но инструкция запуска и UI
каждой сдаваемой ветки описывают только реально доступные возможности.

| Ветка | Возможности | Что отсутствует |
| --- | --- | --- |
| `lab1` | Выборы, heartbeat, term, голос, роли, лидер, состав, UI наблюдения | Пользовательский лог и его репликация, no-op, commit/apply, ReadIndex, KV, CAS, locks |
| `lab2` | Этап 1 + реплицированный упорядоченный список строк, add, локальный просмотр, no-op/commit/apply | KV-команды/кодирование, ReadIndex для KV, CRUD, CAS, locks |
| `lab3` | Этап 2 + детерминированный `string → string` CRUD, линейризуемый GET | CAS, locks, токены, будущие операции в декодере и модели |
| `lab4` | Этап 3 + атомарный CAS, распределённый lock/unlock, HTTP API, клиентский Go API и UI | Не добавляем TTL, транзакции, динамический состав, snapshots, дедупликацию |

Этап 2 — **список строк**, не словарь и не интерпретатор `SET`. Порядок задаёт
лог Raft; одинаковые строки могут встречаться несколько раз.
В этапе 1 RequestVote может сохранять стандартные поля lastLogTerm/lastLogIndex,
но они нулевые; AppendEntries — heartbeat без клиентских записей. Репликация
и логовые ограничения голосования добавляются на этапе 2. Нельзя сохранять
полную реализацию репликации в этапе 1 ради совместимости тестов.

## Безопасная память

1. Storage хранит term, votedFor и (с этапа 2) лог в RAM, синхронно и атомарно
   для вызывающего. Сохраняются контракты копирования, усечения суффикса,
   ошибок и потокобезопасности существующего `raft.Storage`.
2. «Безопасная память» — допущение модели: при допустимом отказе эти данные
   не теряются. Оно не делает обычную RAM долговечной после убийства процесса.
   В unit-тесте перезапуск Raft возможен с тем же объектом Memory Storage;
   KV восстанавливается применением только подтверждённого префикса.
3. На пяти реальных процессах отказ моделируется `docker compose pause`
   / `unpause` (либо отдельно реализованной сетевой изоляцией). Все состояния
   процесса остаются в RAM. При паузе недоступны и HTTP, и RPC: UI и runner
   используют таймауты, не опрашивают паузу как живую ноду. Это не crash-recovery.
4. Процесс с пустой памятью нельзя возвращать в продолжающийся кластер под
   прежним ID: можно повторно проголосовать в term и нарушить Election Safety.
   Не обещать безопасный повторный вход после stop/start.
5. Полное пересоздание **всех** процессов — намеренный сброс стенда: term,
   голоса, лог, KV и locks пусты. Не использовать старые клиентские токены
   в новой жизни кластера; fencing монотонен только внутри одной жизни.
6. Нет файлов состояния, дисковых snapshots/WAL, data volumes или `data_dir`.
   JSON-конфиги, исходники, stdout-логи и статические ресурсы UI остаются допустимы.

## API по этапам

| Маршрут | С этапа | Семантика |
| --- | --- | --- |
| `GET /` | 1 | Встроенный UI текущего этапа без отдельного dev-сервера |
| `GET /status`, `GET /election` | 1 | Локальный статус + участники; alias сохраняется |
| `GET /log` | 2 | Локальный снимок лога, включая неподтверждённый хвост |
| `POST /entries` | 2 | `{"command":"строка"}`, успех 201 после commit и apply |
| `GET/POST/PUT/DELETE /kv/{key}` | 3 | Read/create/upsert/delete строк |
| `POST /kv/{key}/cas` | 4 | `{"expected":"old","value":"new"}` |
| `POST/DELETE /kv/{key}/lock` | 4 | Захват/освобождение; `X-Lock-Token` для доступа |

Начиная с этапа 2, **тот же `GET /status`** включает `entries` и
`consistency: "local"` вместе с `node`/`members`. `node` и `entries` берутся
из одного `InspectLog`, с полями записи `index`, `term`, `kind`, `command`,
`committed`; `/log` сохраняется для совместимости. В этапе 1 нет entries,
commit_index/last_log_index и других полей будущего лога.

Статусы на разных узлах — независимые наблюдения. В UI показывать ID, role,
term, leader_id, voted_for (голос только текущего term), votes (только текущий
кандидат), quorum, running, доступность и время последнего успешного опроса.
Не хранить историю голосов специально: неизвестное/не сохранённое показывать
как неизвестное, а не восстанавливать по итоговому лидеру.

Диагностика локальная и может отставать; не выдавать её за линейризуемое чтение.
Успешная запись означает commit/apply своей пары index/term. Follower направляет
к лидеру через 307; без известного лидера — 503. 504 — неизвестный результат,
409 — конфликт/замена записи, 423 — заблокированный ключ. После таймаута не
повторять изменения автоматически. Лимит строковой команды — 64 КиБ UTF-8.

Этап 3 сохраняет текущую семантику: POST отсутствующего ключа — 201,
повторный POST — 409, PUT — upsert 200, GET/DELETE отсутствующего — 404.
GET использует ReadIndex и ждёт apply. Пустые строки, Unicode и экранирование
должны работать. Произвольный `/entries` не может подделать внутреннюю KV-команду;
с этапа 3 зарезервированный префикс отклоняется.

CAS сравнивает значение, не версию; ABA не обнаруживается. В гонке с одинаковым
expected и **различающимися с expected** новыми значениями выигрывает один.
Lock без TTL и не реентерабельный, отдельно от наличия ключа; удаление значения
не снимает lock. Без/с чужим токеном доступ к занятому ключу — 423, со старым
токеном к свободному — 409. Токен = индекс подтверждённого захвата, воспроизводим
на репликах, следующий успешный захват имеет больший токен. Токен не является
аутентификацией и сам по себе не защищает внешние системы.

«Клиентский API» этапа 4 здесь означает и существующий HTTP-контракт, и небольшой
пакет `client/` на Go: CRUD, CAS, Lock/Unlock, context, обработка 307 и типизированные
ошибки. CLI/отдельный frontend framework в объём не входят.

## UI для сдачи

UI — статические HTML/CSS/JS в `server/`, встроенные в Go-бинарник; без CDN,
Node/npm и отдельного хостинга. Обращения из браузера — через API того же origin.
Если нужен общий опрос пяти нод, серверный диагностический `GET /cluster/status`
агрегирует только статусы известных участников с короткими таймаутами и частичным
результатом. Не добавлять произвольный HTTP proxy и управляющие RPC из UI.
Агрегат явно помечен неатомарным; для данных KV используется обычный API лидера.
Записи с follower UI может перенаправлять серверным same-origin механизмом по
фиксированным участникам, сохраняя 307 для curl/Go-клиента. Способ согласовать
в S1-UI/S2-UI и проверить в браузере: межпортовый fetch не работает без CORS.

- Этап 1: карточки пяти узлов и текущие голоса; недоступность и устаревание видны.
- Этап 2: дополнительно ввод строки и просмотр лога в экране состояния;
  подтверждённые записи, хвост и no-op различимы, результат add содержит index/term.
- Этап 3: CRUD-форма ключ/значение, отдельный результат линейризуемого чтения.
- Этап 4: expected/new CAS, lock/unlock, видимый токен владельца и два клиента
  (две вкладки), понятные 409/423 и неизвестный исход без автоповтора.

Каждый экран показывает номер этапа. Пользовательские строки выводятся как текст,
без HTML-интерпретации. Нельзя рисовать успешную запись до ответа API.
