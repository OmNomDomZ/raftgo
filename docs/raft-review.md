# Ревью ядра Raft

Проверено 11 октября 2026 года: исходники `raft/`, тестовая инфраструктура,
выборы, репликация, коммит, применение, ReadIndex, остановка и восстановление.
Это ревью и проверка сценариев, а не формальное доказательство корректности.
После ревью исправлена гонка ReadIndex и уточнён контракт владения RPC-данными.
Поведение при отказе диска оставлено без изменений по решению автора:
для учебного проекта это принятое ограничение доступности.

## Подтверждённые проблемы

### 1. Исправлено: гонка данных при ReadIndex на follower

Место: [`ReadIndex`, ветка `rf.role != Leader`](../raft/read.go), строки 32–34
на момент ревью; [`notLeaderErrLocked`](../raft/replication.go) и
[`leaderLocked`](../raft/raft.go).

До исправления в этой ветке сначала вызывался `rf.mu.Unlock()`, затем
`rf.notLeaderErrLocked()`. Последний читал `leaderID` без защиты.
Одновременно `HandleAppendEntries` записывает это поле под мьютексом.
Обычное чтение у follower, совпавшее с heartbeat, достаточно для гонки.

Дополнительный тест с двумя горутинами воспроизвёл `WARNING: DATA RACE`:

```text
Write:         HandleAppendEntries → leaderID
Previous read: ReadIndex → notLeaderErrLocked → leaderLocked → leaderID
```

Это подтверждённая ошибка синхронизации публичного API. Само по себе
воспроизведение не показывает нарушение согласованности лога; однако
программа с гонкой не имеет требуемой гарантии безопасного доступа к памяти.

Исправление: `err := rf.notLeaderErrLocked()` формируется до `Unlock`,
затем возвращается сохранённый `err`. Регрессионный тест
`TestReadIndex_FollowerConcurrentHeartbeats` в `raft/read_test.go` одновременно
доставляет heartbeat и проверяет, что follower отказывает в чтении с
корректной подсказкой о лидере; проверка гонки выполняется с `-race`.

### 2. P2: отказ диска лидера может бессрочно остановить запись всего кластера

Место: [`Start`](../raft/replication.go), строки 50–56; в самом коде уже
есть TODO с описанием этого сценария.

Если `StoreLog` постоянно возвращает ошибку, `Start` возвращает ошибку
клиенту, но узел остаётся leader. Его обычные heartbeat не требуют новых
дисковых записей. Followers продолжают отвечать и сбрасывать election
timers, а лидер продолжает успешно проходить CheckQuorum. В итоге два
исправных узла из трёх доступны, но нового лидера не выбирают и все
новые записи завершаются ошибкой.

Проверен локальный сценарий: после отказа fakeStorage десять последовательных
ошибок `Start`, перемежаемых CheckQuorum с ответом одного peer, оставляют
узел лидером. Здесь ответы большинства моделируются напрямую через
`heardFrom`; это проверка переходов состояния, а не отдельный полноценный
сетевой интеграционный тест. Возможность продолжать heartbeat следует
из пути `replicate` / `sendAppendEntries` и обработчика на follower.

Это проблема **доступности**, а не показанная потеря закоммиченных данных.
По решению автора это поведение оставлено как есть: усложнение обработки
отказа диска выходит за нужный объём учебного проекта. TODO в `Start`
сохранён; протокол по-прежнему не обещает доступность записи в этом сценарии.

## Исправлено: неоднозначность контракта владения RPC-данными

Раньше [`RPCHandler`](../raft/transport.go) запрещал сохранять ссылки на
аргументы, хотя внутренний лог сохраняет байты `Command` без глубокого
копирования. Это расходилось с контрактом неизменяемых данных `Transport`.

Теперь оба интерфейса явно задают один контракт: аргументы и ответы,
включая вложенные срезы и байты команд, неизменяемы после передачи.
Обработчик может сохранять ссылки после возврата. Завершение RPC не
разрешает переиспользовать его буферы. Если транспорт декодирует данные
в переиспользуемую память, он должен скопировать их в неизменяемые
выделенные буферы перед передачей обработчику.

Изменена документация контракта, а не стратегия копирования: дополнительной
копии каждой команды в ядре нет. Это согласовано с существующими
контрактами `Start` и `ApplyMsg`, также разделяющими неизменяемые байты.

## Что проверено и выглядит согласованным с протоколом

- Голос и term сохраняются перед выдачей положительного голоса; повторные
  голоса одного peer считаются один раз.
- Свежесть лога сравнивается по term последней записи, затем по индексу.
- Перед успешным AppendEntries проверяется предшественник и сохраняется
  изменённый хвост. Короткий повторный RPC не удаляет совпадающий хвост.
- Follower ограничивает коммит концом проверенного диапазона, а не всем
  своим потенциально расходящимся логом.
- Лидер продвигает коммит по большинству только через запись своего term.
  No-op нового лидера позволяет подтвердить предшествующую историю.
- Поздние ответы не продвигают состояние старой роли/эпохи; больший term
  снимает лидерство даже при недоступном диске.
- Применение идёт по порядку и включает no-op, необходимые для ожидания
  индекса ReadIndex. После рестарта приложение должно строиться заново.
- ReadIndex требует коммита своего term и свежего подтверждения большинства;
  ответы на запросы, созданные до раунда чтения, его не подтверждают.
- RPC и доставка ApplyMsg не удерживают протокольный мьютекс.
  Дисковые вызовы под мьютексом — осознанное решение этого проекта.

Эти выводы относятся к фиксированному согласованному составу кластера,
корректным участникам, неизменяемым командным буферам и хранилищу,
соблюдающему контракт durability. Реального файлового слоя ещё нет;
TODO о семантике ошибок `fsync` остаётся существенным условием его реализации.

## Проверки и воспроизведение

На исходной реализации успешно выполнены:

```sh
go build ./...
go test -count=1 ./...
go test -race -count=1 ./...
go vet ./...
gofmt -l .
```

`gofmt` не вывел файлов. Штатные тесты, в том числе с race detector,
прошли. Дополнительный конкурентный тест обнаружил описанную гонку:
штатный набор не проверял это пересечение обработчиков.

После исправления весь этот набор команд выполнен повторно успешно,
включая новый регрессионный тест в обычном и race-запуске.

Исходник дополнительных проверок сохранён в
[`review-repro_test.go.txt`](review-repro_test.go.txt). Расширение `.txt`
позволяет хранить воспроизведение отдельно от обычного набора тестов.
Go overlay подключает его в пакет `raft`, не меняя исходники пакета.
Из корня репозитория:

```sh
python3 -c 'import json,pathlib; p=pathlib.Path.cwd(); pathlib.Path("/tmp/raft-review-overlay.json").write_text(json.dumps({"Replace":{str(p/"raft/review_repro_test.go"):str(p/"docs/review-repro_test.go.txt")}}))'
go test -race -overlay /tmp/raft-review-overlay.json ./raft -run '^TestReviewReadIndexFollowerRace$' -count=1
go test -overlay /tmp/raft-review-overlay.json ./raft -run '^TestReviewFailedDiskLeaderKeepsLeadership$' -count=1 -v
```

Первый тест на исходной версии завершился с `DATA RACE`; после исправления
он должен проходить. Его усиленный вариант включён в штатные тесты как
`TestReadIndex_FollowerConcurrentHeartbeats`. Как любой
конкурентный stress-сценарий, он не обещает проявление на каждом возможном
планировщике. Второй проходит, когда воспроизводится нежелательное
сохранение лидерства; это диагностический тест текущего поведения,
а не регрессионный тест желаемого исправления.

Ограничения охвата: кластерные тесты исследуют конечное число сценариев,
а `applyLog` узнаёт о коммите из доставленных команд. Поэтому проверка
Leader Completeness этим наблюдателем не охватывает ещё не доставленные
закоммиченные команды; no-op не входит в его карту команд. Это полезные
проверки, но не полное наблюдение всех инвариантов во все моменты времени.

Теоретический ориентир: [статья Raft, Figure 2 и §5](https://raft.github.io/raft.pdf);
для взаимодействия с клиентами — [диссертация Онгаро](https://github.com/ongardie/dissertation).
