# API этапа 3

## HTTP CRUD строк (этап 3)

`POST /kv/{key}` создаёт ключ (201), повторное создание даёт 409 и сохраняет
прежнее значение. `PUT` создаёт или заменяет значение (200). `GET` читает
значение (200), `DELETE` удаляет его (200); отсутствующий ключ для GET/DELETE
даёт 404. Ответ содержит `value`, включая пустую строку; ответ применённой
изменяющей команды также содержит `index`, ошибки — `error`.

Ключ — непустая UTF-8 строка до 1024 байт после URL-декодирования. Передавайте
ключ как один экранированный сегмент пути: например `/kv/a%2Fb` обозначает
ключ `a/b`, а `/kv/a%252Fb` — ключ `a%2Fb`. Unicode, пробелы, `%`, `?`, `#`
допустимы при правильном экранировании. `/kv/` без ключа — 404.

POST/PUT принимают ровно один JSON-объект `{"value":"строка"}`. Имена полей
точные; неизвестные и повторные поля, null, неверные типы, UTF-8 и JSON дают
400 до предложения записи.
Пустые, Unicode и JSON-подобные значения сохраняются как строки. Лимит KV —
65536 байт **всей внутренней команды**: префикс `raftgo:kv:v1:` и JSON с op,
key и value. Поэтому доступный размер значения зависит от
ключа и JSON-экранирования. Входное JSON-тело ограничено 393344 байтами.

Успех записи возвращается после apply именно предложенной пары index/term;
замена записи до commit даёт 409. GET (также HEAD) проходит кворумный ReadIndex
и ждёт применения барьера, поэтому изолированный старый лидер не может выдать
успешное устаревшее чтение. Диагностические `/status` и `/log` остаются локальными.

Follower возвращает 307 с Location лидера, сохраняя экранирование пути и query;
клиент при следовании сохраняет метод и тело. Без известного лидера — 503 с
Retry-After: 1. Сервер не пересылает и не повторяет предложение автоматически.
После пяти секунд ожидания apply изменяющий запрос получает 504 с index, term
и сообщением `outcome unknown`: запись может примениться позже. Автоматически
повторять запрос нельзя; дедупликации нет. Ошибка кворумного барьера GET даёт
503, таймаут ожидания apply чтения — 504.

## Встроенная CRUD-форма (S3-UI)

На `GET /` панель KV сохраняет отдельный выбор узла, ключ и строковое значение.
Create/Get/Put/Delete показывают метод, выбранный узел, ключ, HTTP-код и JSON-ответ
через textContent. GET запускается только кнопкой: результат кворумного чтения
не заменяется локальным опросом состояния/лога. Новый запрос сразу очищает
прежний ответ; неудачное чтение не показывает старое значение как успешное.
Пустая строка видна как `""`, HTML остаётся текстом. 404 означает отсутствие
ключа, 409 — конфликт (точная причина в ответе API), 503 — недоступный лидер
или кворум, 504 записи — неизвестный исход. Автоповторов нет.

Same-origin маршруты `GET/POST/PUT/DELETE /cluster/kv/{id}?key=...` принимают
только ID фиксированного участника и ключ; query позволяет передать также
ключи `.` и `..` без нормализации сегментов браузером. Сервер экранирует ключ
в один сегмент обычного `/kv/{key}` и направляет запрос на API выбранного узла.
Метод и тело сохраняются при 307 только с точным публичным Location известного
участника и тем же ключом; адрес сопоставляется с настроенным internal_api_url.
Циклы/посторонние Location отклоняются. Query, cookies и заголовки клиента
не пересылаются. Дедлайны: сервер 8 с, браузер 9 с; после 503/504 или сетевой
ошибки запрос не повторяется. Retry-After и index/term ошибки API сохраняются.
Маршрут принимает только фиксированных участников и CRUD выбранного ключа.
