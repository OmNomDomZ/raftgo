`lab2` принят на `0006d8422076f19336ad9ab8cdb5a9431fc2d4c6`,

[Правила](AGENTS.md), [подготовка снимков](docs/delivery.md),
[инструкция autokanban](tools/autokanban/README.md).

```sh
./autokanban plan
./autokanban run --max-tasks 2
./autokanban status
```

Внешний dashboard: `python3 scenarios/dashboard.py` (Docker) или
`python3 scenarios/dashboard.py --local`. Кнопки Pause/Resume сохраняют RAM;
завершённый процесс нельзя безопасно вернуть с пустой памятью в прежний кластер.
Встроенный экран выборов, строкового лога и KV CRUD, CAS и lock (этап 4): откройте `GET /` любого доступного узла. Он опрашивает
фиксированный состав через same-origin `/cluster/status`, показывает частичные
результаты и помечает устаревшие данные. Настройте `members[].api_url` так, чтобы
узлы могли обращаться друг к другу; браузеру нужен только адрес открытого узла.
Выберите реплику для просмотра локального лога и отправки строки. Committed,
неподтверждённый хвост и no-op различимы; пустые и повторяющиеся строки допустимы.
Форма работает и с follower, успех показывает index/term после commit/apply.
504 и потеря ответа означают неизвестный исход; автоматического повтора нет.

Учебная реализация Raft на Go: несколько узлов согласуют порядок команд,
переживают потерю части узлов и передают согласованные команды приложению.
CAS использует поля expected и «Значение» (new). Для операций под lock явно
заполните X-Lock-Token или нажмите «Подставить ключ и токен» у токена владельца.
Токены живут только в памяти страницы: другая вкладка их не получает,
перезагрузка/закрытие теряет их. Сохраните токен вручную: восстановления и TTL
нет, auto-unlock не выполняется, в том числе после 504 или смены лидера.
504 означает неизвестный исход; изменения автоматически не повторяются.

Полный прототип содержит ядро протокола в [`raft/`](raft/), KV с CRUD, CAS
и блокировками, HTTP API, транспорт и `storage.Memory`.
[`cmd/raftgo/main.go`](cmd/raftgo/main.go) запускает узел с пустой памятью.
План выделения четырёх этапов — в [канбане](Kanban.md); экран выборов встроен в бинарник.

Этот текст можно читать без знакомства со статьёй о Raft. Примеры `SET` и
`INCR` ниже условные: Raft видит только байты. `/entries` добавляет строку,
а `/kv/{key}` изменяет KV. См. [онбординг](docs/onboarding.md).

## Запуск пяти нод и REST API

```sh
docker compose up --build -d
curl -s http://localhost:8001/status
curl -s http://localhost:8001/election
curl -s http://localhost:8001/log
curl -i -L --max-redirs 5 http://localhost:8001/entries \
  -H 'Content-Type: application/json' \
  --data '{"command":"SET lesson raft"}'
```

Пять API доступны на `localhost:8001`–`localhost:8005`. На старте дайте
кластеру несколько секунд выбрать лидера. `curl -L` следует за HTTP **307**,
сохраняя метод POST и тело запроса. Если лидер ещё неизвестен, API возвращает
**503** с `Retry-After: 1`; повторите запрос после выборов.

| Запрос | Результат |
| --- | --- |
| `GET /status` | Локальный снимок node/entries, consistency=local и участники из конфига |
| `GET /election` | Тот же статус: `role`, `term`, `voted_for`, `votes`, `quorum`, `leader_id` |
| `GET /log` | Локальная копия лога: `index`, `term`, `kind`, `command`, `committed` |
| `POST /entries` | Добавить одну строковую команду: `{"command":"..."}` |

`votes` — количество голосов, полученных **текущим кандидатом**, включая
свой; в остальных ролях равно нулю. `running` показывает, запущен ли узел.
`commit_index` — известная узлу граница коммита, `last_log_index` — конец лога.
Статус — наблюдение самой ноды, а не гарантия актуального лидерства.
Точная семантика полей, локальность и выделение статуса lab1 описаны в
[документации диагностики выборов](docs/api.md).
Выборы запускаются автоматически по таймауту; принудительного назначения
лидера через API нет. Для наблюдения выборов поставьте контейнер лидера на паузу.

Чтение `/log` намеренно локальное: так можно сравнить реплики. Оно может
отставать и включает неподтверждённый хвост (`committed: false`), который
может измениться. Это диагностическое чтение, не линейризуемое чтение KV.
Записи `kind: "noop"` добавляет сам Raft при избрании лидера.

Добавление возвращает **201** и `index`, `term`, `committed: true` только
после коммита и обработки своей пары index/term apply consumer. Максимум команды — 64 КиБ
в UTF-8. **400** означает некорректное тело, **409** — запись была заменена
до коммита. Через 5 секунд без подтверждения возвращается **504** с индексом
и term: результат неизвестен, запись ещё может закоммититься. Автоматической
дедупликации нет; повтор POST может создать вторую запись.

### Конфигурация и данные

Общий [`config/cluster.json`](config/cluster.json) содержит:

- `listen` — адрес публичного HTTP API внутри контейнера;
- `rpc_listen` — отдельный адрес внутренних Raft RPC;
- `members` — фиксированный список узлов: `id`, `rpc_url`, `api_url`.

`rpc_url` использует Docker DNS (`http://node1:9000`), а `api_url` — адрес,
доступный клиенту (`http://localhost:8001`), для редиректов. Для доступа
с другой машины замените `localhost` и настройте публикацию портов в Compose.
ID выбирается аргументом `-id`; конфигурация читается при запуске.
Изменение состава работающего кластера не поддерживается: список должен
совпадать у всех участников. Не меняйте ID и состав работающего кластера.

```sh
go run ./cmd/raftgo -config /path/to/local-cluster.json -id node1
docker compose pause node3   # отказ с сохранением RAM
docker compose unpause node3 # возврат и догон репликации
docker compose logs -f
docker compose down         # полный сброс: следующий up создаст пустой кластер
```

Для запуска без Docker создайте конфиги с уникальными локальными портами
API/RPC; Docker-имена `node1` на хосте не разрешаются.
Большинство из пяти — три: кластер может продолжать записи при потере двух
узлов. Term, голос, лог, KV и locks находятся только в RAM; data volumes нет.
Для отказов используйте pause/unpause: процесс сохраняет всю память.
Убийство процесса теряет её. Нельзя возвращать пустой процесс под прежним ID
в продолжающийся кластер: потеря голоса может нарушить Election Safety.
После полного удаления всех контейнеров новый запуск — пустой кластер;
старые токены в нём использовать нельзя. Автоматический restart отключён.

RPC-порт не публикуется на хост. API публикуется только на loopback; TLS и
аутентификации здесь нет. Кластер рассчитан на доверенную локальную сеть.

## Зачем нужен Raft

Представим три сервера A, B и C, на каждом — словарь ключей и значений.
Хотим, чтобы после падения одного сервера остальные продолжали обслуживать
клиентов и не теряли уже подтверждённые записи.

Просто разослать `SET x=1` всем недостаточно. Одновременно другой клиент
может отправить `SET x=2`. Если A выполнит команды в одном порядке, а B —
в обратном, значения разойдутся. При потере сообщения непонятно ещё и то,
какую команду клиенту можно считать завершённой.

Поэтому сначала согласуем **общую последовательность команд**, а затем
на каждом сервере выполняем её в том же порядке. Последовательность — это
**лог**. Код приложения, выполняющий команды, — **машина состояний**
(state machine). Для одинакового результата она должна быть детерминированной:
одни и те же команды при одном начальном состоянии дают один результат.
Случайные числа и текущее время нельзя независимо выбирать при применении
на каждой реплике; нужные значения следует включать в команду заранее.

Raft управляет логом. Он не разбирает `SET`, не хранит сам словарь и не
выполняет команды вместо приложения.

### Почему нужно большинство

**Кластер** — фиксированный набор участников. **Кворум** здесь — строгое
большинство: `N/2 + 1` при целочисленном делении. У трёх узлов это два,
у пяти — три. Лидер учитывает и себя.

Любые два большинства одного набора участников пересекаются. Например,
из `{A,B}` и `{B,C}` нельзя убрать общий B. В сочетании с правилами голосования
и коммита это не позволяет двум независимым группам утвердить несовместимую
историю. Одного пересечения без остальных правил недостаточно.

При разделении трёх узлов на `{A}` и `{B,C}` группа из двух может выбрать
лидера и продолжить работу. Один A не может подтверждать новые записи.
Это сознательный выбор согласованности: без связи с большинством узел не
может знать, что уже решили остальные.

В модели задания память считается безопасным Storage: допустимые отказы
сохраняют term, голос и лог. На стенде это pause/unpause. Участники следуют
протоколу; завершение процесса не является допустимым восстановимым отказом.
Защита от лгущих участников и подделки сообщений — отдельная задача.

### Три роли и term

| Понятие | Значение |
| --- | --- |
| Follower | Принимает сообщения лидера, голосует, хранит копию лога |
| Candidate | Пытается получить большинство голосов |
| Leader | Принимает команды и рассылает записи остальным |
| Term | Номер попытки выборов / эпохи лидерства, а не время на часах |
| Index | Позиция записи в логе, начиная с 1 |
| RPC | Запрос одного узла другому и ответ на него |
| Heartbeat | `AppendEntries` без новых записей: лидер сообщает, что жив |

Не каждая попытка выборов успешна, поэтому term может пройти без лидера.
В одном term корректный кластер выбирает не больше одного лидера. При
разделении сети старый лидер может ещё считать себя лидером прошлого term,
пока большинство уже выбрало нового. Это не два лидера **одного** term.

Term включён в сообщения. Увидев больший term в допустимом запросе или
ответе, узел принимает его и отказывается от прежнего лидерства/кандидатства.
Запрос с меньшим term отклоняется.

## Что узел помнит

Основная структура — `Raft` в [`raft.go`](raft/raft.go).

| Поле | Смысл | Сохраняется при новом Raft с тем же Memory? |
| --- | --- | --- |
| `currentTerm` | Максимальная принятая эпоха | Да, через `SaveState`; см. оговорку о `dirty` ниже |
| `votedFor` | За кого проголосовал в этой эпохе; пусто, если ещё ни за кого | Да, вместе с term |
| `log` | Последовательность `LogEntry` | Да, через `StoreLog` |
| `role`, `leaderID` | Текущая роль и подсказка, где искать лидера | Нет |
| `commitIndex` | До какой позиции узел знает, что история окончательна | Нет |
| `nextIndex[peer]` | С какой позиции лидер попробует отправить записи этому peer | Нет, только у лидера |
| `matchIndex[peer]` | До какой позиции peer подтвердил совпадающий лог | Нет, только у лидера |
| `votes` | Множество голосов на текущих выборах | Нет |
| `heardFrom` | Кто ответил в текущем окне CheckQuorum | Нет |
| `readRound`, `ackedRound`, `reads` | Учёт запросов чтения и свежих ответов большинства | Нет |

`nextIndex` — предположение, которое может двигаться назад.
`matchIndex` — уже подтверждённый факт, который в рамках одного лидерства
только растёт. Нельзя использовать предположение как подтверждение коммита.

### Устройство лога — начни с открытого `log.go`

Одна запись содержит `Term`, `Kind` и `Command []byte`. Index не хранится
в самой записи: он определяется её положением в массиве.

```text
индекс:    0          1              2              3
term:      0          1              1              2
смысл:   sentinel   no-op        SET x=1          no-op
```

Нулевая запись — фиктивная опора (**sentinel**). Она создаётся в `New`,
не сохраняется в `Storage` и не отправляется приложению. Благодаря ей
пустой лог имеет последний индекс 0, а проверка предшественника первой
настоящей записи не требует особого случая.

`EntryCommand` несёт команду клиента. `EntryNoOp` не меняет словарь,
но занимает полноценный индекс: новый лидер добавляет её для подтверждения
истории в своём term. Зачем это нужно, разберём при коммите.

Вспомогательные функции:

- `lastLogIndexLocked`, `lastLogTermLocked`, `termAtLocked` находят границы и term.
- `entriesLocked(lo, hi)` копирует записи диапазона `[lo, hi)`, чтобы замена
  хвоста массива не испортила уже подготовленный RPC. Это **поверхностная**
  копия: байты `Command` остаются общими и должны быть неизменяемыми.
- `firstIndexOfTermLocked` и `lastIndexOfTermLocked` помогают перепрыгивать
  целые группы конфликтующих записей при ремонте лога.
- `storeLogLocked` сначала сохраняет новый хвост через `Storage`, и только
  после успеха меняет лог в памяти. `from` включён в заменяемый диапазон.
- `checkEntries` проверяет допустимый вид записи и то, что term положительны,
  не убывают и не превосходят term узла/запроса.

### Записано, закоммичено, применено — три разных момента

1. **Записано:** запись существует в Memory отдельного узла. Незакоммиченный
   хвост ещё может быть заменён другим лидером.
2. **Закоммичено:** протокол определил запись как окончательную. Она вместе
   со всем предшествующим префиксом должна сохраниться у будущих лидеров.
3. **Применено:** приложение выполнило команду, например поменяло словарь.

`commitIndex` может опережать приложение. В `apply` локальная переменная
`applied` учитывает доставленные сообщения; факт обработки сообщения
самим приложением должен учитывать уже потребитель `ApplyCh`.

## Как появляется лидер

Маршрут: `Run` → `onElectionTimeout` → `startElectionLocked` →
`requestVote` → на другом узле `HandleRequestVote` → `becomeLeaderLocked`.

`New` загружает состояние и лог, проверяет их и создаёт follower. Таймеры
начинают работать при `Run(ctx)`. `Run` вызывается ровно один раз; после
его остановки нужен новый объект через `New` с тем же Memory (в unit-тесте).
В Docker вместо остановки процесса используйте pause/unpause.

Если follower долго не слышит лидера, он начинает выборы:

1. Перезапускает таймер, чтобы повторить попытку даже при ошибке хранилища.
2. Сохраняет `currentTerm + 1` и голос за самого себя.
3. Становится candidate и рассылает `RequestVote` остальным.
4. Собирает большинство **разных** участников в `votes`.
5. Сохраняет no-op своего term и только затем становится leader.

Свой голос нужно записать до отправки RPC. Иначе узел мог бы проголосовать,
упасть, забыть голос и после рестарта проголосовать за другого кандидата
в том же term. Сохранённый `votedFor` запрещает такое повторное голосование.

### Почему нельзя просто голосовать за первого кандидата

`RequestVote` несёт term кандидата, его ID, индекс и term последней записи.
`HandleRequestVote` разрешает голос только если голос ещё свободен
(или уже отдан этому кандидату) **и** лог кандидата достаточно актуален.

`upToDateLocked` сравнивает сначала term последних записей, потом длину:

```text
мой лог:       последний term=4, index=10
кандидат B:    последний term=3, index=100  → отказ
кандидат C:    последний term=5, index=7    → лог достаточно актуален
кандидат D:    последний term=4, index=9    → отказ
```

Это правило вместе с пересечением большинства и правилом коммита сохраняет
окончательную историю при выборах. Большая длина сама по себе ничего не
доказывает: старый изолированный лидер мог добавить длинный неподтверждённый хвост.

Успешное голосование сбрасывает election timer. Отказ из-за устаревшего
лога — нет: иначе неподходящий кандидат мог бы постоянно мешать выборам.
Повторный запрос того же кандидата безопасен; повторный ответ не даёт ему
дополнительный голос, поскольку `votes` — множество ID.

### Зачем случайные таймауты

При одновременных выборах голоса могут разделиться. Каждый сброс выбирает
новый timeout из `[ElectionTimeoutMin, ElectionTimeoutMax)`, чтобы на
следующей попытке один узел успел начать раньше других.

По умолчанию: election 150–300 мс, heartbeat 50 мс, RequestVote timeout
200 мс, AppendEntries timeout равен heartbeat interval. Это настройки
реализации, а не универсальные значения для любой сети и хранилища.

`electionDeadline` дополнительно защищает от уже полученного старого тика:
если обработчик heartbeat успел сбросить таймер до захвата `mu` циклом
выборов, старый тик не должен начать лишние выборы.

## Как команда проходит через кластер

Пусть A — лидер term 2, no-op на позиции 1 уже закоммичен.
Клиент хочет выполнить `SET x=7`.

```text
клиент → A.Start(command)
          A: сохраняет запись index=2, term=2
          A → B: AppendEntries(prev=1, entries=[2], leaderCommit=1)
          B: проверяет предшественника, сохраняет запись, отвечает success
          A: matchIndex[B]=2; вместе с A получено большинство 2/3
          A: commitIndex=2 → ApplyCh → приложение выполняет SET x=7
          A → B,C: следующие AppendEntries сообщают leaderCommit=2
          B,C: применяют запись, когда имеют подтверждённый префикс до 2
```

Ответ `Start` означает лишь локальное сохранение: `(index, term, nil)`.
Клиентский слой должен дождаться применения **своей** записи. После смены
лидера тот же индекс может занять другая запись другого term.

### Что именно передаёт AppendEntries

| Поле | Для чего нужно |
| --- | --- |
| `Term`, `LeaderID` | Какая эпоха и кто считает себя лидером |
| `PrevLogIndex`, `PrevLogTerm` | Опорная запись перед передаваемым диапазоном |
| `Entries` | Новые записи, возможно пустой список |
| `LeaderCommit` | До какой позиции лидер уже знает о коммите |

`HandleAppendEntries` отвергает устаревший term. Candidate, получивший
сообщение лидера своего term, становится follower. Допустимое сообщение
неустаревшего лидера сбрасывает таймер даже при несовпадении лога: нужно
исправить лог, а не устраивать выборы против работающего лидера.

Затем `appendEntriesLocked` проверяет предшественника. Если на
`PrevLogIndex` нет записи нужного term, принять продолжение нельзя.
Иначе узел ищет **первый действительный конфликт**, заменяет хвост с него
и сохраняет данные до положительного ответа.

Heartbeat проходит ту же проверку предшественника. Пустое `Entries`
не означает «безусловно согласиться со всем логом лидера».

### Почему большинства копий иногда недостаточно

`advanceCommitLocked` собирает последний индекс самого лидера и
`matchIndex` всех peers, сортирует их и выбирает наибольший индекс `n`,
достигнутый большинством. Но продвигает коммит только если
`log[n].Term == currentTerm`.

Вот почему нужна проверка term. В кластере из пяти узлов A мог оставить
запись X из term 2 на A и B. Затем C в term 3 мог быть избран голосами
C,D,E и записать конфликтующую Y только у себя. После этого A может
вернуться, выиграть term 4 голосами A,B,D и скопировать старую X на D.
Теперь X есть на большинстве A,B,D, но если A упадёт, C ещё может выиграть
term 5 голосами C,D,E: последний term его лога 3 новее, чем 2 у D.
Тогда Y вытеснит X. Поэтому считать старую X окончательной только по
количеству копий опасно.

Если же A сначала реплицирует запись **term 4** на большинство, голосующие
с этим префиксом уже не поддержат лог C, заканчивающийся term 3.
Подтверждение записи текущего term закрепляет и весь префикс перед ней.

Для этого новый лидер автоматически пишет no-op: история прошлых term
получает возможность закоммититься даже без новых клиентских команд.
В кластере из одного узла собственная сохранённая запись уже составляет
большинство, поэтому коммит происходит сразу.

## Как исправляются разошедшиеся логи

После сетевого разделения незакоммиченные хвосты могут отличаться:

```text
индекс:       1  2  3  4  5
term лидера:  1  1  2  4  4
term peer:    1  1  2  3  3
```

Лидер начинает с оптимистичного `nextIndex = lastLogIndex + 1`.
Peer отклонит опору `(5,4)` и вернёт `ConflictTerm=3`, `ConflictIndex=4`.
У лидера term 3 нет, поэтому следующая попытка начнётся с индекса 4,
с опорой `(3,2)`. Она совпадает: peer заменит хвост `[3,3]` на `[4,4]`.

Если у лидера есть `ConflictTerm`, он пробует позицию после своей последней
записи этого term. Если peer просто короче, тот возвращает
`ConflictTerm=0` и индекс сразу после своего конца. Так откат обычно
перескакивает сразу группу записей одного term.

Важные ограничения реализации:

- Не обрезать лог просто после конца каждого пришедшего RPC. Запоздалый
  запрос может содержать лишь короткий префикс уже полученных записей.
- Не заменять закоммиченный хвост: попытка конфликта на `index <= commitIndex`
  возвращает `ErrCommittedConflict` без изменения лога.
- На follower коммитировать не дальше
  `min(LeaderCommit, PrevLogIndex + len(Entries))`: более дальний локальный
  хвост этим запросом ещё не проверен.
- Игнорировать обычные результаты RPC прошлой роли/эпохи. Однако больший
  term в допустимом ответе требует немедленно отказаться от старой роли.
- Не уменьшать `matchIndex` по отказу peer: ранее подтверждённый префикс
  не должен исчезать в этом term. Такой ответ логируется как нарушение.

Сравнение совпадающих записей по term, без побайтового сравнения команд,
опирается на единственность лидера и неизменяемость созданных им записей.
Это не механизм обнаружения произвольной порчи данных.

## Пересоздание Raft и ошибки Storage

`storage.Memory` синхронно и атомарно хранит term/голос и заменяет суффикс
лога; копии защищают данные от изменения через входные и выходные срезы.
Вызовы Storage выполняются под `rf.mu`. Ошибки Storage моделируются fake
хранилищами core-тестов: положительный голос или подтверждение AppendEntries
нельзя отправлять, пока соответствующее состояние не сохранено. При принятии
большего term узел снимает лидерство даже при ошибке сохранения (`dirty`).

В unit-тестах новый `Raft` может использовать **тот же объект Memory**.
После `New` роль follower, commit index начинается с нуля. Коммит становится
известен от лидера либо после подтверждения записи собственного term.
Новая машина состояний строится с нуля применением подтверждённого префикса;
неподтверждённый хвост не применяется. Уже восстановленный KV нельзя повторно
проигрывать поверх самого себя. На Docker-стенде pause сохраняет также KV,
locks и applied index; replay при unpause не требуется. Полный новый запуск
всех процессов создаёт пустой кластер. Файлов состояния и восстановления
после kill нет.

## Как безопасно читать

`GetState()` сообщает только локальное представление о лидерстве. Узел
в меньшинстве некоторое время может считать себя лидером, хотя новое
большинство уже записывает другие значения. Чтение его словаря в этот
момент способно вернуть устаревший результат.

`ReadIndex(ctx)` в [`read.go`](raft/read.go) выдаёт границу для
**линейризуемого чтения**: чтение должно учитывать все записи, успешно
завершившиеся до его начала. Пересекающиеся по времени операции допускают
порядок, совместимый с этим требованием.

1. Новый лидер сначала должен закоммитить запись своего term: иначе его
   собственный `commitIndex` может ещё не отражать ранее завершённые записи.
2. Вызов увеличивает `readRound` и будит репликаторы.
3. Лидер ждёт ответы большинства на AppendEntries, подготовленные уже
   для этого раунда или более позднего. Старого ответа недостаточно.
4. Возвращается индекс, через который приложение должно дождаться
   **фактического применения** всех записей.
5. После ожидания приложение читает своё состояние с нужной синхронизацией.

Сам `ReadIndex` не читает KV и не ждёт выполнения команд в приложении.
No-op тоже приходит в `ApplyCh`: словарь она не меняет, но applied index
нужно продвинуть, иначе ожидание чтения может никогда не закончиться.

Ответ о несовпадении лога в текущем term тоже подтверждает контакт для
раунда чтения: peer признал эпоху лидера, хотя его лог ещё отстаёт.
Это отдельно от `matchIndex`, который растёт только при успешной репликации.

`CheckQuorum` решает другую задачу: каждый election timeout лидер проверяет,
ответило ли ему большинство за прошедшее окно. Если нет — становится
follower и отклоняет ожидающие чтения. Эта периодическая проверка помогает
перестать принимать бесперспективные записи, но не заменяет свежий раунд
подтверждения для конкретного чтения.

Путь отказа `ReadIndex` у follower тоже читает состояние под мьютексом:
даже подсказку о лидере нельзя читать одновременно с её изменением без
синхронизации. Этот сценарий проверяет `TestReadIndex_FollowerConcurrentHeartbeats`.

## Как устроена конкурентность

`Run` обслуживает election и heartbeat timers. На каждого peer запускается
свой `replicate`, ещё один работник — `apply`. На выборах запускаются
запросы голосов. Изменяемые поля протокола защищены одним `rf.mu`.

Исходящий RPC выполняется без мьютекса: медленная сеть не должна мешать
принимать сообщения. После ответа мьютекс берётся снова и проверяется,
актуальны ли роль и term. Контекст RPC отменяется при их смене.

На одного peer одновременно отправляется не более одного AppendEntries.
Канал `wake` ёмкостью 1 объединяет повторные сигналы: если работа уже
запланирована, ещё один сигнал не нужен. Отстающий peer получает следующие
пакеты без ожидания очередного heartbeat; размер пакета ограничен
`MaxEntriesPerRPC` (по умолчанию 64 записи).

`apply` тоже использует сигнал ёмкостью 1. Он копирует закоммиченный диапазон
под мьютексом и отправляет его в `ApplyCh` уже без мьютекса. Медленный
потребитель задержит применение, но не удержит протокольный mutex.

Часы заменяемы через `Clock`; даже RPC timeout использует их. В тестах
время можно двигать явно. У `withTimeout` есть особенность:
`ctx.Err()` при истечении таймера — `context.Canceled`, а
`context.Cause(ctx)` — `context.DeadlineExceeded`.

При отмене контекста `Run` останавливает таймеры, отменяет RPC и ждёт своих
работников. Поэтому `Transport` обязан завершать вызовы при отмене `ctx`.
Канал `ApplyCh` узел не закрывает; закрывать его до завершения `Run` нельзя.

## Как подключить приложение

В репозитории есть `storage.Memory` и HTTP-транспорт в `transport/`.
Рабочую сборку узлов можно посмотреть в `testCluster.start` в
[`cluster_test.go`](raft/cluster_test.go); там используются тестовые реализации.

Последовательность интеграции:

1. Реализовать `Storage`, `Transport` и доставку входящих RPC в `RPCHandler`.
   У всех участников должен быть согласованный фиксированный состав кластера.
2. Создать `Config` с собственным `ID`, списком остальных `Peers`,
   хранилищем, транспортом и `ApplyCh`; вызвать `New`.
3. Запустить потребитель `ApplyCh` и `Run(ctx)`. До старта обработчики
   отвечают `ErrNotStarted`; после остановки — `ErrStopped`.
4. Передавать записи лидеру через `Start`. При `ErrNotLeader` можно
   использовать `NotLeaderError.Leader` как подсказку для перенаправления,
   но её нужно считать потенциально устаревшей.
5. Сопоставлять результат `Start` с применением по index и term, а лучше
   также по идентификатору команды. Уведомление может прийти очень быстро:
   обработчик результатов не должен терять его до регистрации ожидающего.
6. Для чтений использовать `ReadIndex` и ожидание applied index приложения.

Байты команды после `Start` и после получения `ApplyMsg` нельзя менять:
код разделяет эти массивы, а не глубоко копирует. Обработчики RPC могут
сохранять ссылки после возврата. Завершение RPC не разрешает переиспользовать
его буферы: транспорт с переиспользуемыми буферами должен скопировать данные
в неизменяемые массивы до передачи обработчику.

Повтор клиентского запроса не становится автоматически «ровно одним
выполнением». Клиент мог не получить ответ на уже выполненную команду.
Для `INCR` повтор изменит результат второй раз. Идентификатор клиента,
номер запроса и дедупликацию должен реализовать прикладной слой.

Пока отсутствуют: снимки/сжатие лога, изменение состава кластера, дедупликация команд,
PreVote. Лог хранится целиком и растёт. Отсутствие PreVote, например,
позволяет долго изолированному узлу накопить большой term и по возвращении
вызвать лишние выборы; это вопрос доступности, а не само по себе потеря данных.

## Проверки и тесты как продолжение учебника

Версия в [`go.mod`](go.mod) — Go 1.27.1.

```sh
go build ./...
go test -count=1 ./...
go test -race -count=1 ./...
go vet ./...
gofmt -l .
```

`-count=1` отключает использование сохранённого результата тестов.
Пустой вывод `gofmt -l .` означает, что форматирование в порядке.

Тесты используют [`fakes_test.go`](raft/fakes_test.go): управляемые часы,
хранилище с отказами и транспорт с потерями, задержками и разделениями сети.
`testing/synctest` помогает дождаться блокировки фоновых работников без
подбора реальных пауз. Это делает сценарии управляемыми; обычный запуск
всё равно не перебирает все возможные конкурентные исполнения.

| Свойство | Что оно запрещает | Где смотреть проверки |
| --- | --- | --- |
| Election Safety | Два избранных лидера одного term | `electionLog.record`, тесты выборов и повторных голосов |
| Leader Append-Only | Лидер переписывает собственные существующие записи | Путь `Start`, no-op; сценарии смены лидера и проверки лога |
| Log Matching | При совпадающих index и term разные префиксы | `testCluster.checkLogs`, тесты ремонта и запоздалых RPC |
| Leader Completeness | Новый лидер теряет ранее закоммиченную запись | `applyLog.checkLeaderCompleteness` при избрании лидера |
| State Machine Safety | Разные команды применяются на одной позиции | `applyLog.record` и сценарии разделений/смен лидеров |

Для последовательного чтения тестов:

1. [`handlers_test.go`](raft/handlers_test.go), [`election_test.go`](raft/election_test.go):
   голосование, смена эпох, поздние ответы, остановка.
2. [`log_test.go`](raft/log_test.go): конфликтующий хвост, проверка опоры,
   ошибки записи и запрет прямого коммита старого term.
3. [`replication_cluster_test.go`](raft/replication_cluster_test.go):
   договорённость кластера, большинство, паузы и возвращение старого лидера.
4. [`stepdown_test.go`](raft/stepdown_test.go): принятие нового term при
   неработающем хранилище и сохранность ранее выданного голоса.
5. [`quorum_test.go`](raft/quorum_test.go), [`read_test.go`](raft/read_test.go):
   потеря большинства, свежесть чтений и ожидание no-op.
6. [`cluster_test.go`](raft/cluster_test.go): случайные отказы и задержки,
   наблюдение за инвариантами в истории кластера.

Например, проследить замену хвоста после возвращения старого лидера:

```sh
go test ./raft -run '^TestCluster_PartitionedLeaderRejoinsAndDropsUncommittedEntries$' -v -count=1
```

Зелёные тесты подтверждают проверенные сценарии, но не являются формальным
доказательством протокола или отсутствия гонок. В [ревью](docs/raft-review.md)
описана найденная и исправленная гонка; её сценарий теперь включён
в штатный набор тестов.

## KV, CAS и распределённые блокировки

KV — строка → строка; значения передаются JSON-строками. Все изменения,
включая захват/освобождение блокировки и неуспешные CAS, проходят через Raft.
Ответ на запись возвращается после применения конкретной записи (index + term).
GET использует ReadIndex и ждёт применения: чтения линейризуемые.
Follower перенаправляет запрос на известного лидера HTTP 307; неизвестный
лидер или недоступный кворум дают ошибку. `/status`, `/election`, `/log`
показывают локальное состояние ноды — обращайтесь к API каждой ноды отдельно.

| Метод | Путь | Тело / назначение |
| --- | --- | --- |
| POST | `/kv/{key}` | `{"value":"a"}` — создать, 409 если существует |
| PUT | `/kv/{key}` | `{"value":"a"}` — создать или заменить |
| GET | `/kv/{key}` | Прочитать; 404 если отсутствует |
| DELETE | `/kv/{key}` | Удалить; 404 если отсутствует |
| POST | `/kv/{key}/cas` | `{"expected":"a","value":"b"}` — атомарно сравнить и заменить; 409 при несовпадении, 404 если отсутствует |
| POST | `/kv/{key}/lock` | Захватить блокировку, ответ содержит `token` |
| DELETE | `/kv/{key}/lock` | Освободить с заголовком `X-Lock-Token` |
| POST | `/entries` | `{"command":"opaque text"}` — добавить произвольную запись в лог |

Ответы на изменения KV содержат `index` и `term` применённой записи,
включая конфликты CAS и отказы доступа. CAS требует ровно строковые поля
`expected` и `value`, без неизвестных/повторных полей. Lock/unlock требуют
пустое тело. `X-Lock-Token` — один заголовок, не список, максимум 1024 байта
UTF-8; неоднозначный или слишком большой заголовок даёт 400 до предложения
команды. Чужой токен проверяется state machine и даёт 423 на занятом ключе.
307 сохраняет путь и query; клиент должен сохранить метод, тело и токен.
504 или потеря ответа означают неизвестный исход: автоматического повтора нет.

Блокировка относится к ключу, в том числе ещё не созданному. Для всех CRUD
и CAS под блокировкой передавайте `X-Lock-Token: <token>`; без правильного
токена возвращается 423. Без блокировки заголовок не нужен. Устаревший токен
на уже освобождённом ключе даёт 409. Удаление значения не снимает блокировку.
Токен — индекс закоммиченного захвата: следующий захват получает новый токен,
включая смену лидера. Это fencing внутри KV; внешние ресурсы сами должны
проверять fencing-токены, если используют такую блокировку.

Блокировки **без TTL**, освобождаются явно и восстанавливаются вместе с KV
повторным проигрыванием подтверждённого лога с тем же Memory. Потеря токена клиентом оставляет
блокировку занятой: автоматического снятия или административного обхода нет.
Токен — средство координации доверенных клиентов, не аутентификация:
диагностический лог доступен через API. Не публикуйте этот учебный API
в недоверенную сеть без отдельного контроля доступа.

Пример (замените URL на API лидера; `curl -L` следует редиректу):

```sh
curl -L -X PUT localhost:8001/kv/message -d '{"value":"hello"}'
curl -L -X POST localhost:8001/kv/message/cas -d '{"expected":"hello","value":"world"}'
curl -L -X POST localhost:8001/kv/message/lock
# Подставьте token из ответа:
curl -L localhost:8001/kv/message -H 'X-Lock-Token: 7'
curl -L -X DELETE localhost:8001/kv/message/lock -H 'X-Lock-Token: 7'
```

Произвольные `/entries` не меняют KV; префикс `raftgo:kv:v1:` зарезервирован
и отклоняется этим endpoint. Ограничение внутренней KV-команды — 64 KiB,
ключа — 1024 байта. Ошибка 504 означает неизвестный исход: запись ещё может
закоммититься. Дедупликации повторов нет; не повторяйте операции вслепую.
Лог и результаты KV-команд пока хранятся без компакции и растут со временем.

Для отладки запустите узел с `-log-level debug`. Логи в stderr имеют JSON-формат:
выборы/смена роли, входящие Raft RPC (включая heartbeat), ошибки RPC,
предложение и применение KV-команд с index/term, применение no-op,
HTTP-запросы с локальным request ID, статусом и длительностью.
Значения KV и токены не добавляются в эти отладочные сообщения.

## Go-клиент

Пакет `raftgo/client`: CRUD, CAS, Lock/Unlock с context и явным токеном,
ограниченные 307 и типизированные ошибки. [Контракт и пример двух клиентов](client/README.md).
При 504 или потере ответа запись имеет неизвестный исход; автоповторов нет,
exactly-once не гарантируется.
