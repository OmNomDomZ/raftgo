# 2. Репликация лога и add

Запуск: `bash scenarios/task2/run.sh` из корня после запуска [стенда](../README.md).
`add` реализован как `POST /entries`, тело `{"command":"demo"}`.

| Шаг | Действие | Ожидаемый результат |
| --- | --- | --- |
| 2.1 | Отправить add follower | `307`, `Location` указывает на `/entries` текущего лидера |
| 2.1 | Отправить add лидеру | `201`, `committed=true`, возвращены `index` и `term`; запись и весь подтверждённый префикс совпадают на пяти нодах |
| 2.2 | Поставить на паузу follower, добавить две записи, вернуть follower | Он догоняет остальные; подтверждённые префиксы совпадают |
| 2.3 | Поставить на паузу лидера, добавить запись новому, вернуть старого | Ранее подтверждённые записи не теряются; все ноды сходятся по префиксу |
| 2.4 | Поставить на паузу три follower и отправить add оставшемуся лидеру | `503` или `504`, подтверждения успеха нет; затем восстановить ноды |

| 2.5 | Приостановить всех follower, отключить три от сети (с сохранением адресов/алиасов), принять неподтверждённый хвост на старом лидере; приостановить его, вернуть три реплики без хвоста и выбрать нового лидера; затем вернуть всех | Старый запрос получает 409 или 504, хвост заменён записью нового term, подтверждённый префикс сохранён на пяти узлах |

В `/log` сравниваются `index`, `term`, `kind`, `command`, `committed`.
Служебные `noop` после выборов нормальны: нельзя ожидать, что первая пользовательская
команда всегда имеет индекс 1. Последний add без кворума может попасть в лог после
восстановления — `504` не гарантирует отсутствие записи.
Итог: `PASS task2`.
