# Сценарии сдачи

Четыре независимых набора проверок текущей реализации. Это этапы демонстрации,
а не исторические версии кода: на каждом этапе запускается один и тот же бинарник,
но проверяется только соответствующая функциональность. `add` в HTTP API — это
`POST /entries` с JSON `{"command":"текст"}`.

## Запуск

Нужны Docker с Compose v2+ и Python 3.9+ на хосте. Сторонние Python-пакеты, jq и
curl для автоматического прогона не нужны. Из корня репозитория:

```sh
docker compose -p raftgo-scenarios -f scenarios/compose.yaml up -d --build
bash scenarios/task1/run.sh
bash scenarios/task2/run.sh
bash scenarios/task3/run.sh
bash scenarios/task4/run.sh
# Или все четыре последовательно:
python3 scenarios/run.py all
```

Один общий Compose достаточен: всем этапам нужны пять нод, диски и один API.
Этот стенд имеет отдельное имя проекта `raftgo-scenarios`, volumes и порты
`18001–18005`. Основной `compose.yaml` можно оставить запущенным. Не меняйте имя
проекта только в команде запуска: runner использует то же фиксированное имя.

Runner ожидает готовность выборов до 30 секунд, проверяет ответы и печатает
`PASS taskN` только после всех проверок. Ошибка завершает процесс ненулевым кодом.
Запускайте сценарии последовательно, без параллельных тестов и ручного отключения
нод. Каждый сценарий создаёт уникальные ключи/команды; очищать диски между запусками
не нужно. После проверки или ошибки runner запускает остановленные контейнеры
обратно и оставляет данные для осмотра. При принудительном завершении runner
восстановите ноды командой `docker compose ... start`.

## Что показывать

| Этап | Сценарий | Основной результат |
| --- | --- | --- |
| 1 | [Каркас и выборы](task1/README.md) | Один лидер, перевыборы, без большинства нет нового лидера |
| 2 | [Репликация и add](task2/README.md) | Подтверждённые записи одинаковы, отставшая нода догоняет |
| 3 | [KV CRUD](task3/README.md) | Значения сохраняются после смены лидера и полного рестарта |
| 4 | [CAS и блокировки](task4/README.md) | Один победитель конкуренции, блокировка сохраняется, старый токен отклоняется |

Все сценарии запускаются через реальные HTTP/RPC и дисковое хранилище.
Они дополняют unit-тесты safety-свойств, но не доказывают корректность Raft при
всех возможных порядках сообщений. Отказы здесь — остановка контейнеров, а не
асимметричные сетевые разделения. Нет гарантии, что тайминговый тест выборов
пройдёт на сильно перегруженной машине.

## Наблюдение и трейсы

На стенде включён `-log-level debug`. Во втором терминале:

```sh
docker compose -p raftgo-scenarios -f scenarios/compose.yaml logs -f --tail=100
# Только одна нода:
docker compose -p raftgo-scenarios -f scenarios/compose.yaml logs -f node1
# Статус и локальный лог конкретной ноды:
curl -s http://127.0.0.1:18001/status | python3 -m json.tool
curl -s http://127.0.0.1:18001/log | python3 -m json.tool
```

Ищите выборы/смену роли и term, `request vote RPC`, `append entries RPC`,
`entry applied`, `kv proposed`, `kv applied`, HTTP-запросы и ответы.
`/status`, `/election` и `/log` показывают локальное состояние без редиректа.
`/log` может временно отставать; runner ждёт совпадения подтверждённого префикса.
На follower операции записи и KV-чтения возвращают `307 Location` на лидера,
когда он известен, либо `503`, если выборы ещё идут.

## Остановка

```sh
# Остановить стенд и сохранить данные:
docker compose -p raftgo-scenarios -f scenarios/compose.yaml down
# Только если нужен полностью чистый демонстрационный стенд — удалить его диски:
docker compose -p raftgo-scenarios -f scenarios/compose.yaml down -v
```

Ответ `504` означает неизвестный исход записи: она может подтвердиться после
восстановления кворума. Сценарии не считают такой ответ гарантированным откатом
и не повторяют автоматически неопределённую запись.
